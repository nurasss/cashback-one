# Gemini: срочные правки кабинета по замечаниям Инны — 2026-11-12

## Роль и границы

Новое решение владельца: Claude отвечает за backend и приложение; Gemini — за лендинг и фронтенд кабинета. В этой задаче править только `admin/`, собственные материалы проверки и отчёт. Backend можно читать, но не менять, не запускать его проверки параллельно с Claude и не коммитить его изменения. Куратор код продукта не правит.

Прочитать целиком `AGENTS.md`, `CLAUDE.md`, `docs/PROMPT_ADMIN_LANDING_OWNER_REVISIONS_2_2026-11-11.md`, `docs/PROMPT_ADMIN_LANDING_OWNER_REVISIONS_2_CONTINUE_2026-11-12.md`, `docs/PROMPT_CLAUDE_INNA_BACKEND_2026-11-12.md`. Текущий файл уточняет роли и добавляет требования; незакрытые frontend-пункты прежних заданий сохраняются.

**Упало или неожиданно — СТОП и безопасный сырой вывод; без самостоятельных исправлений и повторных мутаций; секреты и персональные данные скрыть.** Это относится и к собственным скриптам проверки/съёмки. Только при `apply_patch verification failed` разрешено перечитать файл и один раз применить патч по фактическому тексту, записав случай в отчёт; повторный отказ — СТОП.

## 1. Срочно: не сохраняется период оборота

Речь о периоде расчёта статуса, поле `turnover_period_months`, а не о фильтре дат дашборда. Инна сообщает, что изменение перестало сохраняться. Сначала воспроизвести на текущем коде в изолированной среде, не объявлять причину заранее.

Проследить форму статуса, валидацию, POST/PATCH, полученный ответ, инвалидацию кеша и повторный GET. Проверить создание и редактирование, повторное открытие формы, перезагрузку страницы и смену активного бизнеса. Не подменять неудачный ответ API локально сохранённым значением и не показывать успешное сохранение при ошибке.

Исправить только подтверждённую frontend-причину. Если проблема в API, записать точный путь, безопасные поля запроса/ответа и ожидаемый контракт для Claude; не исправлять backend самому. Если без нового API продолжение невозможно — остановиться и сообщить зависимость.

## 2. Процент кэшбэка по статусу

В исходниках уже есть поле `percent`; не создавать второе и не переписывать форму с нуля. Дать бизнесу понятное редактирование «Кэшбэк, %» / корректный KK-перевод для каждого статуса вместе с порогами оборота и периодом. Проверить сохранение и повторное чтение процента, включая дробное значение и ошибки диапазона 0–100. Не добавлять персональное переопределение процента карты: владелец поручил настройку по статусам.

Решение владельца: сервер определяет статус по сумме покупок за выбранный период, процент задаёт бизнес. Пример Инны про 1%, месяц и 200 тысяч не является разрешением заменить текущие настройки этими значениями. Понижение при снижении оборота — серверная задача. Не обещать, что изменение процента в кабинете автоматически меняет начисление ONE/Cash: такой интеграции пока не подтверждено.

## 3. Пагинация карт

В списке карт добавить «Страница X из N» и KK-эквивалент, переходы назад/вперёд с корректными недоступными состояниями. Сервер уже возвращает `limit`, `offset`, `has_more`, но этого недостаточно для точного N. Claude готовит серверный `total`: считать число страниц по общему количеству с теми же поиском, фильтром бизнеса и правами доступа. Все карты ради подсчёта не загружать.

Пустой список показывать понятным пустым состоянием, без «1 из 0». При смене поиска/бизнеса возвращаться на первую страницу. Обработать сокращение списка, когда текущая страница стала недоступна. Проверить согласованность с существующим компактным отображением строк: кнопка раскрытия таблицы не заменяет пагинацию. До доступности согласованного API не имитировать точное N.

## 4. Форма контента

По замечанию Инны рядом с загрузкой картинки указать реальные рекомендуемые размеры/соотношение сторон и ограничения формата/веса, аналогично подсказкам заставки. Сначала определить целевую форму по существующему контексту и её полям: изображение, начало/конец показа, сортировка. Если однозначно определить форму нельзя — СТОП с конкретным вопросом, без массового изменения всех форм и без выдуманных размеров.

На desktop начало показа, конец и сортировку разместить в одну строку. На телефоне обеспечить читаемый перенос. Убрать лишний вложенный скролл, не скрывая недоступные поля/кнопки и не обрезая диалог. Сохранять возможность прокрутить длинную форму.

## Проверки и результат

Перед правками зафиксировать `git status --short -- admin` и diff; чужую работу не откатывать, не делать checkout/restore/reset/stash/clean. Перед патчем читать актуальный файл. Сначала адресные тесты воспроизведения и исправления, затем полный admin-тест, lint, typecheck, build — последовательно. Не чинить неожиданно упавший baseline самостоятельно.

Проверить менеджера и суперадминистратора, RU/KK, 1366×768 и 390×844. Для периода и процента нужны не только статичные снимки, но и проверка сохранения → повторного GET → повторного открытия → перезагрузки. Для пагинации проверить фильтры, пустой список и последнюю страницу. Моки не доказывают исправление рабочего сайта; явно отделять локальную интеграцию от production.

Собственные снимки и безопасные результаты — `reports/inna-admin-2026-11-12/`; отчёт — `reports/INNA_ADMIN_2026-11-12.md`: воспроизведение, установленная причина, изменения, API-зависимости, сырые результаты проверок, просмотренные снимки с SHA-256, непроверенное. Старый отчёт не выдавать за выполнение новых пунктов.

Без deploy, APK, изменения манифестов, production-записей, коммита и push. Новое ограничение на коммит имеет приоритет над прежним заданием. После локального результата — СТОП для независимой приёмки.
