## 1. Первичная диагностика на принятом production-коде

Не проверять гипотезы на всём dirty backend: принят production-архив unrestricted
statistics SHA-256 eac534bf8d490777b028a76e29f846c48d61912dfc50de0bf1edad17fe8360e1.
Сверить актуальность базы read-only; исключить неопубликованные lifetime и прочие правки.

### Статусы

В видео первый уровень меняется [0,200000) → [0,300000) при соседях [100000,200000)
и [200000,+∞). Это конфликт диапазонов, а не повод отключить валидацию.
Исследовать точный HTTP-код/ошибку на локальной синтетической копии этой шкалы;
проверить и допустимое редактирование с успешным PATCH/повторным чтением.
Не сдвигать границы соседей автоматически и не менять production-каталог.

Сохранить исключение для редактирования legacy-пересечения при неизменных границах,
но не расширять его на новые пересечения. Сохранить max>min, неотрицательные суммы,
десятичную точность, права и tenant-изоляцию. Предложить безопасный специфичный
machine-readable error/field path для конфликта оборота (не общую поломку всех CONFLICT).
При изменении контракта согласовать с Gemini обратную совместимость и RU/KK-сообщения.
Сырой английский message с данными не выводить в UI как решение.

Если реально нужна новая атомарная операция изменения всей шкалы — сначала описать
точную причину/варианты и остановиться до реализации; бизнес-политику соседних порогов
не придумывать. Проценты/пороги примера 350/700 тысяч не назначать автоматически.

### Баннеры и акции

Проверить текущую schema/service-проверку starts_at (15 секунд) и эффект minute-rounded
«Начать сейчас»: при now=10:21:40 значение 10:21:00 отклоняется, null принимается.
Gemini должен передавать null для немедленного режима; не ослаблять backend-валидацию
прошлых дат вместо исправления семантики UI. Проверить также редактирование старого
старта без изменения и точность секунд, бессрочный конец, явный будущий старт,
невалидный/обратный период, обе роли, kind banner/offer, поля изображения.
Доказать отсутствие других причин 422 на payload из синтетического воспроизведения.
Для валидных новых баннера/акции выполнить настоящие POST → GET → PATCH → GET
на локальном стенде; не считать upload изображения сохранением контента.

## 2. Доставка обновлённого каталога в приложение

На изолированном backend с временной БД и разрешённой синтетической сессией:
сохранить валидный threshold/name/percent/image, проверить commit, рост
loyalty_tiers_version, смену ETag и полный обновлённый /me/app-content.
Запрос со старым ETag должен дать 200 с новыми данными, со свежим — 304.
Для невалидного PATCH не должно быть частичного изменения/роста версии.

Проверить настоящий consumer mobile: foreground/ручной refresh, принадлежность
бизнесу, offline cache и различие каталога/минимального fallback от неподтверждённого
личного статуса. Не включать lifetime-расчёт и не обещать его как часть исправления.
Моки, интеграционный локальный стенд, реальный HTTPS и Android явно разделить.
Если проверка установленной 1.0.26 на Android недоступна — это открытая граница,
не задача владельцу повторять очевидно доступные локальные проверки.
