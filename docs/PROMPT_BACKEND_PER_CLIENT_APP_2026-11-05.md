Решение владельца: у каждого клиента своё Android-приложение со своим пакетом (например `kz.cashbackone.keremet`), а сервер, база и кабинет общие. Общее приложение `kz.cashbackone.mobile` остаётся рабочим. Один покупатель (один номер телефона) может пользоваться приложениями нескольких клиентов на одном телефоне.

Сейчас сервер этого не различает:

1. **Push.** `push_service.send_to_user` и `has_active_device` (`backend/app/services/push_service.py`) берут **все** устройства покупателя. Код списания магазина А придёт и в приложение магазина Б. `Device.app_id` (пакет) сохраняется при `PUT /me/push-token`, но не используется.
2. **Списки.** `GET /me/promotions`, `GET /me/notifications`, `GET /me/cards` (и связанные бейджи и отметки «просмотрено») возвращают данные по всем бизнесам покупателя.

## Задача

### 1. Пакет приложения у бизнеса

- Миграция `0016`: в `businesses` поле `android_app_id` (строка до 255, может быть `NULL`, уникально среди не-`NULL`). Формат проверять тем же правилом, что и `app_id` в `PushTokenRegisterRequest`. Вниз — удаление поля.
- Кабинет и API суперадмина: показать и изменить поле может только `superadmin` (существующий маршрут изменения бизнеса или отдельный, на твой выбор с обоснованием). Менеджер бизнеса поле видит, но не меняет. Кабинет `admin/`: поле на странице бизнеса, RU/KK, подсказка «Пакет Android-приложения клиента, например kz.cashbackone.keremet. Пусто — только общее приложение».

### 2. Push только в нужное приложение

Для события бизнеса B (код списания, будущие рассылки) подходящие устройства покупателя такие:
- если у B задан `android_app_id`: устройства с `app_id == B.android_app_id` **и** устройства общего приложения `kz.cashbackone.mobile`. Значение общего пакета вынести в настройку `PUSH_SHARED_APP_ID` со значением по умолчанию `kz.cashbackone.mobile`;
- если не задан: только общее приложение.

`has_active_device` и `send_to_user` получают `business_id` (или список допустимых `app_id`) и применяют то же правило. Значит, `CUSTOMER_NO_APP` в `/pos/redemptions` тоже учитывает бизнес. Остальная логика без изменений: отключение недействительных токенов, временные ошибки, маскирование кода.

### 3. Фильтр по бизнесу в приложении

Необязательный параметр `business_id` (UUID) в `GET /me/cards`, `GET /me/promotions`, `GET /me/promotions/{id}`, `POST /me/promotions/seen`, `GET /me/notifications`, `POST /me/notifications/read`, `GET /me/badges` и `POST /me/cards/bind` (для привязки: если номер карты принадлежит другому бизнесу, ответ такой же, как для несуществующей карты, без раскрытия, что карта есть):
- без параметра — как сейчас, ответ побайтно прежний: старые APK должны работать;
- с параметром — только данные этого бизнеса. Чужая акция по `id` → тот же 404, что и для несуществующей;
- бизнес, в котором у покупателя нет карты, → пустой список (не 404), кроме `GET /me/promotions/{id}`;
- ETag и кеш (если есть) учитывают параметр.

## Тесты

- push: у покупателя три устройства (общее, `keremet`, `other`). Списание `keremet` (с `android_app_id`) → общее и `keremet`, `other` не получает. Бизнес без `android_app_id` → только общее. Только устройство `other` → `CUSTOMER_NO_APP`;
- уникальность `android_app_id`, неверный формат → 422, менеджер не может изменить;
- каждый эндпоинт из п. 3: без параметра ответ как раньше, с параметром фильтруется, чужая акция → 404;
- миграция вверх и вниз на временном PostgreSQL (`POSTGRES_TEST_URL`, `APP_ENV=test`, как в прежних отчётах).
