Отдельный диагностический EXE и прежнюю цепочку исследования метаданных НЕ продолжать. Работа по кабинету сохраняется отдельно, не терять незакрытые замечания.

Прочитать AGENTS.md, CLAUDE.md, reports/KEREMET_STATUS_DATA_2026-11-09.md и текущие контракты синхронизации. Исполнитель — Gemini (agent/backend). Mobile делает Claude по принятому контракту, его файлы не менять.

## Подтверждённые условия

- Только Keremet: <100000 ₸ — уровень 1 «Нет-нет заглядывает», 2%; 100000 <= оборот <200000 — уровень 2 «Продуктовый эксперт», 3%; >=200000 — уровень 3 «Шоппинг-босс», 4%.
- Окно скользящее: последние 6 календарных месяцев, не 180 дней и не фиксированное полугодие. Корректно вычитать месяцы с учётом последнего дня месяца, использовать бизнес-время Казахстана UTC+5, не часовой пояс сервера/компьютера.
- Источник истины ONE. Процент/статус в облаке не меняет реальные правила начисления Cash. Не вычислять сумму покупки из баланса/суммы бонусов/деления на процент.

## 1. Проверить существующий источник, не строить отдельный инструмент

В agent/src/poscenter_loyalty_agent/stage0/data_profile.py функция profile_spend_total_realism уже содержит кандидат `СуммаЧека` в `ОстаткиБонусныхКарт`. Рабочий one_com_source.py читает движения этого регистра, но берёт только сумму бонусов. Это точка входа для доработки, не доказательство полноты данных настоящей ONE.

Проследить имеющиеся безопасные отчёты/маппинг и код: доступен ли СуммаЧека, что означает на нескольких строках одного чека, у расходов/возвратов и покупок с 0 бонусов. Сам старый Stage0 на клиенте не запускать, маппинг/выводы целиком в Git не класть. Если сведений о семантике не хватает — перечислить конкретно недостающие факты и какой агрегат из уже существующих журналов/данных нужен, а не создавать новый EXE. Не делать производственный запрос и не утверждать готовность данных на основании моков.

## 2. Подготовить доработку agent/backend

Выбрать минимальное расширение существующего потока: передавать реальные суммы покупок/возвратов со стабильной идентичностью источника либо подтверждённый агрегат за окно. Обосновать выбор в отчёте, сохранить совместимость старого агента и других клиентов. Нельзя просто суммировать СуммаЧека по всем бонусным строкам, если чек повторяется.

Обязательно:
- Отдельные денежные поля/Decimal, не подменять transaction.amount бонусов суммой покупки.
- Не удваивать чек из-за нескольких бонусных движений, lookback, повторной отправки, обновления записи, полного resync.
- Учитывать возвраты и аннулирования по реальной семантике источника; непонятные движения не считать покупками молча.
- Состояние, курсоры и HMAC не сбрасывать, старые записи/подписи должны читаться после обновления. Миграции локального состояния — совместимые и тестируемые, без запуска на рабочих путях.
- Продумать начальную загрузку покупок за полные 6 месяцев: уже импортированная бонусная история не содержит нового поля, обычная пустая дельта сама его не заполнит. Планировать контролируемое дополнение данных с сохранением state, без автоматического сброса DB/full_resync клиента.
- Явно различать подтверждённый нулевой оборот и неизвестный/неполную историю. Отсутствие покупок в облаке не является доказательством нулевого оборота.
- Пересчитывать уровень при выпадении покупок из окна даже без новой продажи. Указать свежесть расчёта и период, чтобы приложение не принимало устаревший all-time spend_total за rolling-оборот.
- Сохранить API старых APK и правил других бизнесов; не включать loyalty_tiers или turnoverConfirmed на production сейчас.

Если полнота источника пока не доказана, можно подготовить совместимое расширение и тесты, но подключение неподтверждённого источника должно оставаться выключенным. Не выдавать прототип за работающий личный статус.
