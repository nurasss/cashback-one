# Gemini: узкое продолжение после остановки К5 E2E

СТОП task-1016 принят правильно. Это разрешение на ограниченную диагностику,
исправление проверочного сценария и один новый прогон, не на изменение продукта.
Прочитать этот документ и сохранить текущие frontend-правки без отката.

## Найдено куратором чтением

В scripts/verify_admin_eleven_items_final_20261116.py новый статус получает
image_url=https://media.local.test/media/tier4-secret.webp прямым заполнением URL.
Такая картинка не загружалась и не регистрировалась. В принятом backend
_verify_scoped_tier_image требует разрешённый путь вида
promotions/<32 hex>.webp и существующий медиа-объект, доступный этому бизнесу.
Тестовый tier4-secret.webp не проходит уже формат пути. При достижении этой
проверки корректный ответ — 422, а не 201. Фактический ответ task-1016 неизвестен:
AssertionError не сохранил статус и тело; не выдавать вывод по коду за его запись.

## Разрешённые действия

1. В проверочном скрипте сохранять перед assert фактический status и безопасное
   JSON-тело ошибок POST/PATCH/PUT; не писать Authorization/cookie/токены/пароли.
   Локальные данные синтетические. Сохранить task-1016 как исходное падение.
2. Создание статуса в положительном К5-сценарии провести с настоящей загрузкой
   синтетического изображения через input[type=file] диалога и POST /admin/media/images
   в том же изолированном бизнесе. Дождаться успешного upload, взять фактический URL
   ответа и проверить его использование в POST tier. Ожидать POST 201 как прежде.
3. Оставить проверку, что image_url и описание отсутствуют в аудите, но проверять
   фактический загруженный URL, а не удалённый выдуманный tier4-secret.webp.
4. Если нужно проверить отказ по выдуманной ссылке, выделить отдельный негативный
   сценарий с ожидаемой ошибкой и отсутствием успешного аудита. Не заменять
   положительный сценарий ожиданием 422. Не подменять ответ POST мок-успехом.
5. Запустить один полный изолированный E2E на уже принятом чистом backend-архиве
   b7e03da17cfc92143073d8f5519e7f66d79ee3f966d874baf4dc5c6a9b731b10.
   Если фактическая причина иная или возникнет новая ошибка — СТОП, status/body
   и сырой обезличенный traceback; без следующей серии самостоятельных правок.

Разрешены только проверочный скрипт/его данные и новые отчётные артефакты.
Backend, продуктовый frontend, правила image_url, tenant-проверки и серверные
ограничения не менять ради прохождения теста. Не регистрировать фиктивный URL
прямой записью в БД для имитации загрузки; использовать штатный HTTP upload.
Настоящее FTPS и production не трогать: стенд по-прежнему InMemoryMediaStorage.
