# Customer Authentication Architecture (TASK-003)

В этом документе зафиксирована архитектура обратной аутентификации покупателей через WhatsApp (Reverse Flow), модель сессий, ротация токенов и границы интеграции с провайдером сообщений.

---

## 1. Архитектура Reverse WhatsApp Flow

В соответствии с разделом 4 ТЗ `TZ_loyalty_app_v1.1`, для входа покупателей в мобильное приложение используется схема **обратной авторизации**:

```text
Мобильное приложение           Облачный бэкенд               WhatsApp / Wappi
        │                             │                              │
        │─── 1. POST /auth/challenge ─▶│                              │
        │    {"device_id": "..."}     │                              │
        │                             │ (Создание challenge, TTL 3м) │
        │◀── 2. challenge_id, code ───│                              │
        │       wa.me URL             │                              │
        │                             │                              │
        │─── 3. Переход по wa.me ───────────────────────────────────▶│ (Приложение WA)
        │       Отправка code на бизнес-номер                        │
        │                             │                              │
        │                             │◀── 4. Webhook провайдера ────│ (Входящее сообщение)
        │                             │    confirm_login_challenge   │
        │                             │    (pending -> confirmed)    │
        │                             │                              │
        │─── 5. GET /auth/challenge ─▶│                              │
        │    Header: X-Device-Id      │ (Атомарный обмен на токены,  │
        │                             │  confirmed -> consumed)      │
        │◀── 6. Access JWT, Refresh ──│                              │
```

## 2. Жизненный цикл Challenge (`LoginChallenge`)

| Статус | Описание | Допустимые переходы |
|---|---|---|
| `pending` | Одноразовый код сгенерирован, ожидается отправка покупателем в WhatsApp | $\rightarrow$ `confirmed`, $\rightarrow$ `expired` |
| `confirmed` | Входящее сообщение подтверждено внутренним сервисом подтверждения (`phone` зафиксирован) | $\rightarrow$ `consumed` |
| `consumed` | Токены успешно выданы мобильному приложению при первом обращении | Терминальный статус |
| `expired` | Истек срок жизни (TTL 3 минуты) | Терминальный статус |

### Правила и инварианты:
* **Формат кода:** ровно 8 символов, безопасный криптографический алфавит без неоднозначных символов (`23456789ABCDEFGHJKMNPQRSTUVWXYZ`, исключены `0/O`, `1/I/L`).
* **Безопасность хранения:** открытый код отдается мобильному приложению только в момент создания. В базе данных хранится **исключительно HMAC-SHA256 digest** (`AUTH_CHALLENGE_HASH_KEY`). Открытый текст кода в БД не сохраняется.
* **Уникальность и retry-механизм:** поле `code_hash` защищено уникальным ограничением `uq_login_challenges_code_hash`. При генерации challenge выполняется retry-цикл (до 5 попыток) с откатом savepoint при маловероятной коллизии; при исчерпании попыток возвращается контролируемый `500 Internal Server Error` (`CHALLENGE_GENERATION_FAILED`) без утечки деталей СУБД.
* **Срок действия (TTL):** 180 секунд (3 минуты).
* **Привязка к устройству (Device Binding):** Запрос статуса и обмен на токены требует заголовок `X-Device-Id`. Идентификатор нормализуется (strip whitespace, длина от 1 до 128 символов). Если идентификатор устройства не совпадает с владельцем challenge, запрос отклоняется с кодом `403 Forbidden` (`DEVICE_MISMATCH`). Пустой заголовок или состоящий только из пробелов отклоняется (`400` / `422`).
* **Одноразовость (Single-Use):** Подтвержденный challenge обменивается на сессию и токены **ровно один раз**. Повторный опрос использованного challenge возвращает `409 Conflict` (`CHALLENGE_ALREADY_CONSUMED`).

## 3. Rate Limiting (Ограничение частоты запросов)

Перед созданием challenge проверяются лимиты запросов:
* **Лимит на устройство:** `auth_challenge_device_limit` (по умолчанию 5 запросов за окно).
* **Лимит на IP-адрес:** `auth_challenge_ip_limit` (по умолчанию 20 запросов за окно).
* **Временное окно:** `auth_challenge_rate_window_seconds` (по умолчанию 300 секунд).
* **Реализация:** Multi-process safe через Redis (`RedisRateLimiter`) с использованием атомарного Lua-скрипта (INCR + EXPIRE на 1-м запросе без сброса TTL). Для тестирования используется детерминированный in-memory ограничитель (`InMemoryRateLimiter`).
* **Отказоустойчивость (Fail-Closed):** При недоступности Redis во время запроса `/auth/challenge` возвращается контролируемый `503 Service Unavailable` (`AUTH_RATE_LIMIT_UNAVAILABLE`) без трейсбеков и без обхода лимитов.
* **Управление соединениями:** Общий клиент Redis управляется через FastAPI lifespan (`main.py`) с корректным закрытием пула соединений (`aclose()`) при завершении процесса.
* При превышении лимита возвращается `429 Too Many Requests` (`RATE_LIMIT_EXCEEDED`), и challenge в БД не создается.

## 4. Идентификация покупателя (`User Identity`)

* Подтвержденный номер телефона отправителя является подтвержденной личностью покупателя.
* **Инвариант:** `one normalized phone -> one User`.
* В базе данных наложено ограничение `UNIQUE(phone)` на таблицу `users`.
* Сервис `get_or_create_user_by_phone` использует атомарный dialect-safe `ON CONFLICT (phone) DO NOTHING` с последующим чтением существующего `User.id`, что полностью сохраняет существующие настройки профиля пользователя (например, выбранный язык `kz`).
* Все номера приводятся к каноническому стандарту E.164 (`+7XXXXXXXXXX`). Номер бизнес-аккаунта WhatsApp валидируется строгим регулярным выражением E.164 (`^\+[1-9]\d{7,14}$`).

## 5. Токены и модель сессий (`AuthSession`)

После подтверждения challenge мобильное приложение получает пару токенов:

### 1. Access Token:
* **Формат:** JWT (JSON Web Token), алгоритм `HS256`.
* **Срок жизни:** 15 минут (`access_token_ttl_seconds = 900`).
* **Полезная нагрузка (Claims):**
  - `sub`: UUID пользователя (`User.id`).
  - `sid`: UUID сессии (`AuthSession.id`).
  - `typ`: `"access"`.
  - `iat`: Unix timestamp выпуска.
  - `exp`: Unix timestamp истечения срока.
* В токене отсутствуют конфиденциальные данные (баланс, штрихкод, пароли).

### 2. Refresh Token:
* **Формат:** Криптографически стойкий непрозрачный токен (48 байт энтропии, префикс `rfr_`).
* **Срок жизни:** 30 дней (`refresh_token_ttl_seconds = 2592000`).
* **Хранение:** В таблице `auth_sessions` хранится **только SHA-256 хэш** токена (`refresh_token_hash`).

### 3. Ротация Refresh-токенов (`POST /auth/refresh`):
* При каждом обновлении токенов старый refresh-токен немедленно инвалидируется.
* Генерируется новый refresh-токен и обновляется его хэш в строке сессии (`last_rotated_at = utcnow()`).
* Повторное использование старого refresh-токена пресекается (`401 INVALID_REFRESH_TOKEN`).
* Конкурентная безопасность: захват блокировки строки сессии (`with_for_update`) гарантирует, что из двух одновременных запросов с одним токеном выиграет ровно один.

### 4. Выход из системы (`POST /auth/logout`):
* По переданному refresh-токену фиксируется `revoked_at = utcnow()`.
* Все последующие попытки refresh для этой сессии отклоняются.
* Выход из одной сессии не затрагивает другие устройства и активные сессии того же пользователя.

## 6. Входящий Webhook Wappi (TASK-004)

В рамках TASK-004 реализован production-ready адаптер входящего вебхука Wappi:

* **Эндпоинт:** `POST /webhooks/wappi`.
* **Спецификация интеграции:** полная документация зафиксирована в [WAPPI_WEBHOOK_CONTRACT.md](file:///Users/nuras/Desktop/cashback-one/docs/WAPPI_WEBHOOK_CONTRACT.md).
* **Аутентификация вебхука:**
  - Статус заголовка: `WAPPI_AUTH_HEADER_NAME = NOT VERIFIED`.
  - Имя заголовка не имеет дефолта в коде и конфигурируется явно через `WAPPI_WEBHOOK_AUTH_HEADER`.
  - Секрет проверяется с использованием алгоритма постоянного времени `hmac.compare_digest`.
  - При отсутствии заголовка или несовпадении секрета возвращается `401 Unauthorized` (`INVALID_WEBHOOK_AUTH`).
* **Защита от перегрузки (Payload Guard):**
  - Ограничение размера входящего тела через `WAPPI_WEBHOOK_MAX_BODY_BYTES` (по умолчанию 64 КБ). При превышении возвращается `413 Payload Too Large`.
* **Изоляция профиля (Profile Isolation):**
  - Обрабатываются сообщения только от инстанса `WAPPI_LOGIN_PROFILE_ID`. Сообщения других профилей игнорируются (`ignored_profile`).
* **Идемпотентность и аудит сообщений:**
  - Таблица `wappi_webhook_events` с уникальным ограничением `(profile_id, message_id)`.
  - Concurrency-safe speculative insert (`ON CONFLICT (profile_id, message_id) DO NOTHING`).
  - При повторной доставке того же `message_id` возвращается `200 OK` с `result: "duplicate"`, исключая повторные подтверждения и ошибки `IntegrityError` (HTTP 500).
* **Фильтрация и валидация:**
  - `wh_type` должен быть строго `"incoming_message"`.
  - `type` сообщения должен быть строго `"chat"`.
  - Групповые чаты (`@g.us`, `chat_type != dialog`) отклоняются.
  - JID отправителя валидируется по маске `^(\d{10,15})@c\.us$`, номер нормализуется в E.164.
  - Код авторизации валидируется: длина 8 символов, только символы из криптографического алфавита.
* **Атомарность и Retry-семантика:**
  - Подтверждение challenge через `confirm_login_challenge(session, code, sender_phone, commit=False)` и фиксация статуса в `wappi_webhook_events` коммитятся в рамках единой транзакции СУБД.
  - При возникновении сбоя БД или инфраструктурной ошибки транзакция немедленно откатывается (`ROLLBACK`), возвращается контролируемый `503 Service Unavailable` (`WEBHOOK_PROCESSING_UNAVAILABLE`).
  - Ошибка не фиксируется как терминальный статус `error`, резервация отменяется, что сохраняет возможность безопасной и успешной повторной обработки при provider retry.
* **Изоляция номеров (Second-Phone Attack Protection):**
  - При попытке подтвердить уже подтвержденный challenge другим номером телефона возвращается `already_confirmed_other_phone` без раскрытия номера первого покупателя.
