# Claude: срочный backend кабинета и контракт оборота — 2026-11-12

## Роль и границы

По решению владельца Claude отвечает за backend и приложение; Gemini — за лендинг и frontend кабинета. Сейчас приоритет — backend-баг сохранения периода статуса и поддержка правок кабинета. Приложение, агент, ONE и production этой задачей не менять. `admin/` можно читать, но не править. Перед началом убедиться, что Gemini больше не меняет backend; если подтверждения нет — запросить его через владельца до правок.

Прочитать целиком `AGENTS.md`, `CLAUDE.md`, `docs/PROMPT_ADMIN_LANDING_OWNER_REVISIONS_2_2026-11-11.md`, `reports/BACKEND_OWNER_REVISIONS_2_2026-11-12.md`, `docs/PROMPT_GEMINI_INNA_ADMIN_2026-11-12.md`. Старый `docs/PROMPT_AGENT_PURCHASE_TURNOVER_2026-11-09.md` читать как исследовательский контекст, не как разрешение запускать его реализацию или применять прежние фиксированные пороги.

**Упало или неожиданно — СТОП и безопасный сырой вывод; без самостоятельных исправлений и повторных мутаций; секреты и персональные данные скрыть.** Ожидаемый красный regression-тест на воспроизведение именно заявленного бага разрешён: до запуска назвать ожидаемое утверждение и результат; только такое заранее обозначенное падение не останавливает исправление. Любая другая ошибка, включая падение прежнего теста с устаревшим ожиданием, требует остановки. Не менять фикстуры для сокрытия baseline. Исключение для патча: при первом `apply_patch verification failed` перечитать файл и один раз повторить по фактическому тексту с записью в отчёт; повторный отказ — СТОП.

## 1. Срочно: сохранение периода оборота

Проверить `turnover_period_months` в конфигурации статусов, а не период фильтра дашборда. Проследить POST/PATCH → схема → сервис → commit → GET → данные приложения. Сопоставить актуальный frontend-запрос чтением кода/передачи Gemini. Установить, где теряется значение, либо доказать, что backend его сохраняет; не заявлять заранее ни серверную, ни frontend-причину.

Начальная точка — существующее незакоммиченное дерево, не HEAD. Уже внесённую работу Gemini и Claude сохранить, не переписывать. Проверить создание, редактирование только периода, повторный GET в новой сессии БД, изоляцию бизнесов, полномочия менеджера, некорректные и null-значения. Если причина на фронте — передать Gemini точный контракт и безопасное воспроизведение, не менять `admin/`.

## 2. Процент кэшбэка статуса

Поле `percent` и API статусов уже существуют. Проверить и при необходимости исправить именно сохранение настроек процента по статусам: число 0–100, дробные значения, без float-искажений денежных расчётов, без персонального override карты. Проверить повторное чтение и выдачу настройки приложению, версию/инвалидацию серверного контента при изменении, изоляцию бизнесов и прав. Не подменять сохранённый период или процент значениями по умолчанию при частичном PATCH.

Настройка в облаке не означает изменения начисления на кассе. ONE остаётся источником балансов и начислений, агент только читает. Не реализовывать запись в ONE/Cash и не создавать облачные бонусные движения.

## 3. Поддержка пагинации карт

Для списка карт и используемого им поиска добавить обратно совместимое серверное поле `total`: точное количество карт, соответствующих тем же фильтрам, поиску и tenant-scope, что и `items`. Сохранить `items`, `limit`, `offset`, `has_more`, текущие ограничения размера страницы и сортировку. Не расширять общий Page для всех API без необходимости; выбрать минимальный согласованный контракт.

Зафиксировать для Gemini структуру ответа, условия поиска/фильтрации и семантику total. Тесты: несколько страниц, пустой результат, последняя/недоступная страница, поиск, разные бизнесы и роли, отсутствие утечки общего количества чужих карт. Не считать все карты в браузере и не отдавать лишние персональные данные. Допускать обычные изменения количества между запросами; не обещать стабильный снимок при параллельной синхронизации.

## 4. Новые правила статусов: пока только контракт и план

Владелец подтвердил: статус определяется подтверждённым оборотом покупок за выбранный период; пороги и процент каждого статуса задаёт бизнес в кабинете. При выпадении покупок из окна статус понижается даже без новых покупок. Процент не выводить обратным делением бонусов на чек. Примеры Инны «около 1%», «месяц», «200 тысяч» не являются окончательными параметрами.

Нужна передача реальных сумм покупок из ONE через существующий агент в backend, затем серверный расчёт и отображение в приложении. Сумма бонусов не равна сумме покупки. Подтверждённый нулевой оборот отличать от неизвестного. Учитывать возвраты, аннулирования, повторные строки одного чека и идемпотентность. Семантика `СуммаЧека` пока не подтверждена. Не включать расчёт личных статусов и не подменять источник моками.

На этом этапе подготовить только список подтверждённых фактов, недостающих сведений и минимальный контракт агент → backend → приложение; отметить различие скользящего окна и календарного месяца, если новое требование не позволяет однозначно выбрать. Старое решение Keremet — последние 6 календарных месяцев — не заменять молча новым значением. Указать, как будут согласованы серверный статус и фактический процент начисления Cash. Исследование агента/ONE и реализация потока оборота — отдельное поручение после согласования контракта.

Фраза «все с нуля, старых не переносим» не определена достаточно: никаких удалений карт, обнулений балансов, смены ключей, сброса SQLite/HMAC/курсоров, полной пересинхронизации или исключения существующих покупателей. Приветственные бонусы не реализовывать до согласования суммы, однократности, условий и источника начисления ONE/Cash.

## Проверки и результат

До правок — статус/diff `backend/` и адресный baseline. Без checkout/restore/reset/stash/clean и откатов чужой работы. После — адресные regression-тесты, затем полный backend-прогон и проверки стиля/типов по известному baseline. Проверки сохранения и количества выполнить также на изолированном PostgreSQL; если среды нет, сообщить, не направлять тесты в production и не запускать миграции на рабочей БД. Новую миграцию не добавлять без установленной необходимости и отдельного согласования; новые номера сверять с актуальным деревом, 0018/0019 заняты.

Сырые безопасные результаты — `reports/inna-backend-2026-11-12/`; отчёт — `reports/INNA_BACKEND_2026-11-12.md`: причина бага либо доказательство его отсутствия на сервере, изменённые файлы, API для Gemini, проверки и ограничения, отдельно план передачи оборота. Не выдавать локальные тесты за исправление production.

Существующий блокер приложения — воспроизводимое падение предупреждения push с холодным кешем — не снят этим заданием. Не прогревать кеш ради зелёной приёмки и не объявлять приложение готовым к выпуску.

Без APK, deploy, изменения версий/манифестов, рабочих данных, коммита и push. После локального результата — СТОП для независимой приёмки.
