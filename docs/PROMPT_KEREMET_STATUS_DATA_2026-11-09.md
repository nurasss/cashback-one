# Gemini: подготовить статусы Keremet и проверить оборот за 6 месяцев — 2026-11-09

Прочитать AGENTS.md, CLAUDE.md, backend/app/services/loyalty.py, backend/app/schemas/wallet.py, модели Business/Card и пути синхронизации spend_total, docs/AGENT_API.md §2.4, текущие маппинг/контракты агента без секретов. Сохранить всю параллельную работу admin/mobile. Это отдельная задача после доработок кабинета.

**Упало или неожиданно — СТОП и сырой вывод; без самостоятельных исправлений и повторных мутаций; секреты и персональные данные скрыть.**

## Решение владельца

Только Keremet, оборот **за последние 6 месяцев от текущей даты**, не фиксированное полугодие. Пороги в тенге без пересечений:

- level 1, «Нет-нет заглядывает», threshold 0, percent 2: оборот <100000.
- level 2, «Продуктовый эксперт», threshold 100000, percent 3: 100000 <= оборот <200000.
- level 3, «Шоппинг-босс», threshold 200000, percent 4: оборот >=200000.

ONE остаётся источником правды. Задача не разрешает менять начисления, балансы, документы и настройки ONE или Cloud ради соответствия процентам. Отображение процента в приложении не доказывает применение его кассой.

## Первый этап: проверка, без изменений production

1. Проследить, кто реально заполняет spend_total и что это за показатель: покупки за всё время, шесть месяцев или отсутствующее значение. Не предполагать, что поле означает rolling 6 months. Проверить чтением исходников и при необходимости SQL READ ONLY агрегатами без карт/телефонов/ключей; не выводить клиентский маппинг и конфиг целиком.
2. Установить, достаточно ли данных ONE для корректного оборота. Начисления/списания бонусов не являются суммами покупок — не вычислять оборот из них. Если источник за шесть месяцев не подтверждён, не настраивать как будто статус уже достоверный. Нужен честный блокер и минимальный план получения данных только чтением. Не запускать Stage0, COM-регистрацию, сброс state и полную синхронизацию.
3. Зафиксировать правило rolling-окна: шесть календарных месяцев от даты расчёта, даты/время и бизнес-часовой пояс, возвраты/аннулирования, пересчёт при выпадении покупок из окна даже без новой покупки. Если семантика ONE расходится — описать, не подменять полгода 180 днями молча.
4. Подготовить точный payload loyalty_tiers для keremet, путь применения штатным кабинетом/API и план отката к исходному значению с защищённой копией. Ничего не применять до приёмки куратора. Проверить существующее поведение tier_info(None): оно считает null нулём и может выдать базовый уровень. Не выдавать неизвестный оборот за подтверждённый 0. Если нужна правка контракта/агента — предложить конкретные файлы и тесты для следующего этапа, не менять их самовольно.
5. Согласовать с отчётом для Claude минимальные поля: реальные name/percent, период и неизвестные значения. Не менять поведение остальных бизнесов и API для старых APK без плана совместимости.

Отчёт `reports/KEREMET_STATUS_DATA_2026-11-09.md`: факты/источники без секретов, доступность rolling-оборота, payload трёх уровней, требуемые изменения/проверки/откат и нерешённые вопросы. Без commit/push, deploy, изменений рабочей БД, ONE, агента и конфигурации клиента. Это исследование и подготовка настройки, не завершённое внедрение.
