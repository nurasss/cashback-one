# CANDIDATE — контракт атомарного редактора шкалы статусов (backend)

**Статус: CANDIDATE.** Технический контракт изолированного backend-кандидата, не согласованное изменение production API и не опубликован. Frontend **не внедряет** его до приёмки куратором и отдельного решения о выкладке. Старый backend (production) этих маршрутов не имеет — реализовать за feature-detection (404/405 на `GET …/scale` ⇒ работать по-прежнему через PATCH).

База: production-архив `eac534bf…60e1`. Отчёт: `reports/ADMIN_SCALE_AND_DELIVERY_CANDIDATE_2026-11-16.md`.

## 1. Маршруты

Только `BusinessLoyaltyTier` (не legacy `loyalty_tiers` JSON). Права — как у существующих tier-операций: `business_manager` своего бизнеса и `superadmin`; чужой бизнес → `404 ADMIN_RESOURCE_NOT_FOUND`; без входа → 401/403 (как у остальных `/admin/*`). Миграции не нужны (Alembic остаётся `0019`).

### `GET /admin/businesses/{business_id}/loyalty-tiers/scale`
```json
{
  "business_id": "uuid",
  "version": 7,
  "tiers": [ { …BusinessLoyaltyTierAdminItem… } ]   // порядок level, priority, id; ВСЕ строки (и неактивные)
}
```
`version` = `businesses.loyalty_tiers_version` (тот же счётчик, что в `/me/app-content.loyalty_tiers_version`). Деньги — строки `"100000.00"`, `max_turnover: null` = без верхней границы.

### `PUT /admin/businesses/{business_id}/loyalty-tiers/scale`
```json
{
  "expected_version": 7,
  "tiers": [
    { "id": "uuid", "min_turnover": "0",       "max_turnover": "300000", "percent": "2" },
    { "id": "uuid", "min_turnover": "300000",  "max_turnover": "500000", "percent": "3" },
    { "id": "uuid", "min_turnover": "500000",  "max_turnover": null,     "percent": "4.5",
      "name_ru": "…", "name_kk": "…", "description_ru": null, "description_kk": null,
      "image_url": "https://…/media/promotions/<uuid>.webp", "is_active": true }
  ]
}
```
Ответ `200`:
```json
{ "business_id": "uuid", "version": 8, "changed": true, "tiers": [ …итог после сохранения, как в GET… ] }
```

Правила тела:
- `expected_version` ≥ 1 — **версия из последнего GET**. `tiers` — **все** существующие строки бизнеса ровно по одному разу (1…100 элементов).
- Обязательны в каждой строке: `id`, `min_turnover` (≥0, ≤14 цифр, ≤2 знака), `max_turnover` (**ключ обязателен**, значение число или `null`), `percent` (0…100, ≤2 знака). Числа — строки или JSON-числа; `true/false` отвергаются.
- Необязательные (если ключ опущен — значение **не меняется**): `name_ru`, `name_kk` (1…120, не null), `description_ru`, `description_kk` (≤2000, `null` очищает), `image_url` (`null` очищает; новая должна быть загружена этим же бизнесом через `/admin/media/images`), `is_active` (не null).
- **Не принимаются** (422, `extra=forbid`): `level`, `priority`, `turnover_period_months`, `business_id`, `created_at`… — порядок/уникальные ключи в этой операции не меняются. Создание/удаление строк — прежними POST/DELETE.
- Сохраняется **итоговое состояние**: промежуточных состояний нет. Версия растёт **ровно на 1** независимо от числа изменённых строк. Если фактических изменений нет — `200`, `changed:false`, версия, ETag и аудит **не меняются**.

## 2. Ограничения конечной шкалы (действующие, не новые)
- `max_turnover > min_turnover` для каждой строки.
- Среди **активных** строк (после сохранения) диапазоны `[min,max)` не пересекаются; касание границ (`max_A == min_B`) допустимо; `null` = ∞. Непрерывность/разрывы не требуются. Неактивные строки в проверке не участвуют.
- Исключение для legacy: пара пересекающихся строк допускается только если **обе** были активны и остаются активными с **теми же** границами (то есть сохранение ничего не меняет в этой паре — например, правка текста/процента на старой шкале Keremet). Любое изменение границы/активности, создающее или сохраняющее пересечение, отклоняется. Новую шкалу, снимающую legacy-пересечение (границы обеих строк меняются), принимает.
- Деньги/процент/картинка — те же проверки, что у PATCH (в т.ч. принадлежность картинки бизнесу: чужая → 403, неизвестная → 404, не https → 422).

## 3. Ошибки (все в виде `{"error": {code, message, reason, …}}`; `message` — служебный английский, в UI не показывать)

| HTTP | `code` | `reason` | Доп. поля | Что делать UI |
|---|---|---|---|---|
| 409 | `CONFLICT` | `LOYALTY_SCALE_VERSION_CONFLICT` | `current_version` | «Шкала изменена другим пользователем» → перечитать GET, показать актуальную, не терять ввод без подтверждения |
| 409 | `CONFLICT` | `LOYALTY_SCALE_RANGE_OVERLAP` | `conflicts:[{tier_id, other_tier_id, levels:[a,b], fields:["tiers[i].min_turnover","tiers[i].max_turnover","tiers[j]…"]}]` | подсветить поля обеих строк; текст «Диапазоны уровней {a} и {b} пересекаются» |
| 422 | `VALIDATION_ERROR` | `LOYALTY_SCALE_INVALID_RANGE` | `tier_id`, `fields:["tiers[i].max_turnover"]` | «Максимум должен быть больше минимума» у строки |
| 422 | `VALIDATION_ERROR` | `LOYALTY_SCALE_INCOMPLETE` | `tier_ids` (пропущенные) | перечитать GET (набор изменился) |
| 422 | `VALIDATION_ERROR` | `LOYALTY_SCALE_UNKNOWN_TIER` | `tier_ids` (эхо присланных) | перечитать GET |
| 422 | `VALIDATION_ERROR` | `LOYALTY_SCALE_DUPLICATE_TIER` | `tier_ids` | ошибка клиента — не должна случаться |
| 422 | `VALIDATION_ERROR` | — | `message` вида `body.tiers.0.percent: …` | схема: числа, знаки, лишние поля |
| 403/404/422 | прежние | — | — | ошибки картинки как у PATCH |
| 404 | `ADMIN_RESOURCE_NOT_FOUND` | — | — | чужой/несуществующий бизнес |

Проверка порядка: 404 (доступ) → 409 версия → 422 состав набора/диапазон → 409 пересечение → картинки. Версия проверяется **до** состава: устаревший клиент получает 409 версии, а не «неполный набор».

Аддитивно для **прежних** `POST …/loyalty-tiers` и `PATCH …/{tier_id}`: при пересечении тот же `409 CONFLICT` и английский `message`, плюс новые необязательные ключи `reason:"LOYALTY_TIER_RANGE_OVERLAP"`, `fields:["min_turnover","max_turnover"]`, `conflicts:[{tier_id, level, name_ru, name_kk, min_turnover, max_turnover}]` (все пересечённые). Остальные 409 (дубль level/priority) этих ключей не имеют.

## 4. Конкурентность и аудит
- Внутри одной транзакции: блокировка строки бизнеса → блокировка строк шкалы → проверка `expected_version` → запись → `version+1` → аудит. Из восьми одновременных сохранений с одним `expected_version` успешно ровно одно; остальные 409 версии (проверено на PG16).
- `POST/PATCH/DELETE` tier теперь тоже берут блокировку бизнеса первой (монотонная версия, одинаковый порядок блокировок); их поведение для клиента не изменилось.
- Аудит: одна запись `loyalty_scale_updated` / `business_loyalty_scale` на успешное изменение; `before_state`/`after_state` содержат только `version` и по строкам `tier_id, level, min_turnover, max_turnover, percent, is_active` (без названий, описаний, картинок). Отказы аудита не создают.

## 5. Рекомендации для UI
1. Редактор шкалы: открыть GET → форма всех строк (границы, процент, активность) → одна кнопка «Сохранить шкалу» → PUT с `expected_version` из GET. После 200 заменить локальное состояние ответом PUT.
2. Не пересчитывать и не двигать соседей автоматически; границы вводит владелец. Локальные подсказки (max>min, пересечения) допустимы, но решение за сервером.
3. Отправлять **только** обязательные числа + реально изменённые необязательные поля; ничего не стирать молча (опущенные ключи сохраняют значение).
4. Деньги — строками, `null` для «без верха». Запрет локального ввода `e`, `-`, >2 знаков.
5. Тексты ошибок RU/KK строить по `reason`, не по `message`; для неизвестного `reason` + 409 показывать общее «Конфликт сохранения, обновите страницу».
6. Пример шкалы 350000/700000 и тестовая шкала из тестов — **не** значения по умолчанию и не предложение владельцу.

## 6. Что не включено
Миграции; изменение level/priority; создание/удаление строк внутри PUT; новые правила непрерывности; legacy `loyalty_tiers`; личный lifetime-статус и кассовый процент; серверные push при смене шкалы.
