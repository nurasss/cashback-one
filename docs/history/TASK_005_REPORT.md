## 2. Реализованные компоненты и архитектурные решения

### 2.1. Защита Customer API (Access JWT & Session Invalidation)
Реализованы FastAPI-зависимости `get_current_user` и `get_current_customer` в `backend/app/api/deps.py`:
* **Bearer Token Extractor:** извлечение токена из заголовка `Authorization: Bearer <access_token>` с валидацией схемы (отклонение некорректных форматов с кодом 401 `INVALID_AUTHORIZATION_HEADER`).
* **Криптографическая верификация:** декодирование JWT через `decode_access_token` с проверкой подписи `HS256`, срока жизни (`exp`) и обязательных клеймов (`sub`, `sid`, `typ="access"`).
* **Контроль сессии (Session Revocation Enforcement):**
  * По `sid` выполняется проверка записи в таблице `auth_sessions`.
  * Если `auth_sessions.revoked_at IS NOT NULL` (после вызова `/auth/logout` или админского отзыва), запрос отклоняется с HTTP 401 `SESSION_REVOKED`.
  * Если `auth_sessions.expires_at <= utcnow()`, запрос отклоняется с HTTP 401 `SESSION_EXPIRED`.
  * Проверяется соответствие `auth_sessions.user_id == sub`.
* **Проверка активности аккаунта:** проверка `users.deleted_at IS NULL` (отклонение деактивированных пользователей с кодом 401 `USER_NOT_FOUND`).

### 2.2. Автопривязка карт по номеру телефона (`auto_bind_cards_by_phone`)
Функция реализована в `backend/app/services/wallet_service.py` и автоматически вызывается при каждом обращении к `GET /me/cards`:
* **Нормализация номера:** сопоставление по E.164 (`Card.phone == normalize_phone(user.phone)`).
* **Multi-Business поддержка:** связываются все непривязанные карты пользователя во всех организациях (бизнесах).
* **Инвариант единственного владельца (`uq_user_cards_card_id`):** карта не может принадлежать двум пользователям одновременно. Если карта уже привязана к другому пользователю, автопривязка исключает её перехват и логирует предупреждение.
* **Защита скрытых карт:** если карта ранее была мягко скрыта пользователем (`hidden_at IS NOT NULL`), автопривязка **никогда** не сбрасывает этот флаг и не возвращает её в список активных.
* **Конкурентная безопасность (PostgreSQL):** вставка через `pg_insert(UserCard)...on_conflict_do_nothing(index_elements=["card_id"])` гарантирует отсутствие `IntegrityError` или HTTP 500 при одновременных запросах.

### 2.3. Эндпоинты кошелька покупателя (`/me/*`)
Зарегистрированы в `backend/app/api/customer_wallet.py` и подключены в `backend/app/main.py`:
1. **`GET /me/cards`**:
   * Возвращает список всех активных карт покупателя (`hidden_at IS NULL`).
   * Включает информацию о бизнесе (`id`, `name`) и брендинге (`logo_url`, `primary_color`, `accent_color`).
   * Баланс карты форматируется строго как 4-значная строка (`"1250.5000"`), исключая ошибки представления чисел с плавающей точкой (`float`).
2. **`GET /me/cards/{card_id}`**:
   * Возвращает детальные данные карты.
   * **IDOR Protection:** если карта не принадлежит пользователю или скрыта, возвращается унифицированный HTTP 404 `CARD_NOT_FOUND` без утечки метаданных.
3. **`DELETE /me/cards/{card_id}`**:
   * Мягкое скрытие карты из кошелька покупателя (`user_cards.hidden_at = utcnow()`).
   * Запись в `cards` **НЕ** удаляется, баланс и статус блокировки сохраняются.
   * Возвращает HTTP 204 No Content. Повторный вызов возвращает HTTP 404.
4. **`GET /me/cards/{card_id}/transactions`**:
   * Детерминированная пагинация по курсору (`occurred_at DESC, id DESC`).
   * Поддержка параметров: `limit` (1..100, по умолчанию 20), `cursor` (base64 keyset `occurred_at|id`), `type` (опциональный фильтр по типу операции: `accrual`, `redemption` и др.).
   * Точные 4-значные строковые представления для полей `amount` и `balance_after`.
   * Полная изоляция IDOR (HTTP 404 при запросе транзакций по чужой или скрытой карте).
