## 2. Concurrency Strategy (Стратегия конкурентности)

Выбран механизм: **Tenant-Level Transaction Row Locking** (`SELECT id FROM businesses WHERE id = :business_id FOR UPDATE`).

### Почему выбран этот механизм:
1. **Строгая изоляция тенантов:** Блокируется только конкретная строка текущей организации в таблице `businesses`. Запросы агентов организации А и организации Б выполняются абсолютно параллельно без малейшей взаимной блокировки.
2. **Гарантия согласованности в режиме Read Committed:** В стандартном режиме изоляции транзакций PostgreSQL (Read Committed) при ожидании освобождения блокировки второй запрос после ее получения видит актуальный снимок базы данных, зафиксированный первым запросом. Это позволяет безопасно проверять существование строк, сравнивать временные метки снимков и выявлять дубликаты.
3. **Межпроцессная надежность:** Блокировка удерживается ядром СУБД (PostgreSQL), что делает ее устойчивой к масштабированию приложения на множество рабочих процессов (Gunicorn/Uvicorn workers) или контейнеров Kubernetes (в отличие от `asyncio.Lock`, работающего строго в памяти одного процесса).
4. **Портативность и детерминированность:** Механизм прозрачно поддерживается в SQLAlchemy и корректно компилируется как для PostgreSQL, так и для SQLite в тестах, не требуя сложных диалект-специфичных выражений `INSERT ... ON CONFLICT RETURNING`.

## 3. Database Atomicity (Атомарность на уровне БД)

- Обработка каждого HTTP-запроса (`POST /agent/sync/cards` и `POST /agent/sync/transactions`) выполняется в рамках единой транзакции базы данных.
- Захват блокировки тенанта происходит в первой строке обработчика до выполнения каких-либо SELECT-запросов.
- При возникновении любой ошибки валидации (некорректный телефон, превышение лимита, неизвестная карта) транзакция откатывается (`rollback`), исключая частичное применение пакета.

## 4. Card Race Protection (Защита от гонок при создании и обновлении карт)

- **Сценарий одновременной вставки новой карты:**
  - Два параллельных запроса отправляют одну и ту же новую карту (`barcode = "1111222233334"`).
  - Запрос 1 захватывает блокировку тенанта, видит отсутствие карты, выполняет `INSERT` и `COMMIT`.
  - Запрос 2 ожидает снятия блокировки. После получения блокировки его SELECT возвращает уже сохраненную Запросом 1 карту.
  - Запрос 2 не пытается выполнить повторный `INSERT`, исключая `IntegrityError` (код 500).
  - В БД сохраняется ровно 1 запись.
- **Сценарий гонки устаревших данных (Stale Protection):**
  - Исходное состояние: `10:00 / balance = 100`.
  - Одновременно приходят Запрос A (`11:00 / balance = 200`) и Запрос B (`12:00 / balance = 300`).
  - Если Запрос A выполняется первым: он обновляет карту до 11:00 / 200. Затем Запрос B видит 11:00, понимает, что 12:00 > 11:00, и обновляет карту до 12:00 / 300.
  - Если Запрос B выполняется первым: он обновляет карту до 12:00 / 300. Затем Запрос A видит 12:00, условие `11:00 > 12:00` ложно, обновление отклоняется (`ignored_stale += 1`).
  - **Итог:** Вне зависимости от очередности выполнения финальное состояние в БД строго равно `12:00 / balance = 300`.

## 5. Transaction Replay Protection (Идемпотентность транзакций)

- Композитный ключ `(card_id, external_id)` защищен ограничением `UNIQUE` на уровне схемы.
- Благодаря блокировке тенанта два конкурентных запроса с одинаковым `external_id` сериализуются:
  - Первый запрос вставляет запись (`created=1, duplicates=0`).
  - Второй запрос видит существующую запись в `existing_keys` и фиксирует дубликат (`created=0, duplicates=1`).
  - Оба запроса возвращают HTTP 200 OK. Ошибок 500 или необработанных `IntegrityError` не возникает.
  - В БД сохраняется ровно 1 транзакция.
