## Подтверждённая исходная точка

Аудит 15.11: HEAD `2b576ea`, production-миграция ранее 0019; шесть сверенных production-модулей
совпали с HEAD. Сессия 14 суток, `/admin/me` без новых обязательных полей локального frontend,

Это основание, а не разрешение пропустить свежий preflight.

## Что включить

1. Сессию покупателя 365 дней со скользящим продлением при успешном refresh.
   Сохранить ротацию, отзыв, защиту от повторного старого refresh, logout и ограничения кабинета.
   Проработать существующие сессии без удаления и массового выхода: явно описать,
   как живой старый refresh получает новый срок; не обещать оживления уже истёкших токенов.
2. Согласованный `/admin/me`: `admin_max_stats_period_days` и логотип бизнеса.
   Сверить вложенность и обязательность с `admin/src/auth/session.ts`, не только прежним отчётом.
3. Календарные границы дашборда UTC+5, валидацию дат и единый лимит периода.
4. Серверные пользовательские строки «бонусы» вместо «баллы» в применимых RU/KK путях.
5. Точные счётчики/пагинацию и поиск карт без утечки чужого бизнеса, без изменения контрактов
   остальных списков по догадке.
6. Совместимость форм статуса **без периода и без пользовательского priority**:
   create/PATCH/GET, сохранение остальных полей и процента, версия каталога и ETag.
   Старое поле БД не удалять миграцией только ради скрытия UI; не применять период к lifetime.
7. Передачу изменений каталога в `/me/app-content`: новый контент после изменения,
   старый ETag не даёт ошибочный 304, права бизнесов сохраняются. Не путать с личным уровнем.

## Главный риск состава кандидата

Нельзя выложить всё текущее `backend/` или старый /tmp-архив вслепую. В дереве есть разные
пакеты, включая lifetime и дополнительную валидацию. Старые manifests — основание сравнения,
не готовый полный список для этого этапа.

Собери вне рабочего дерева snapshot с перечнем файлов/hunks и SHA-256. Отдельно покажи:
что из прежнего принятого пакета; что нужно для совместимости новых форм; что исключено.
Не переписывай рабочее дерево ради изоляции. Не брать р1/r2 архив как замену обычному пакету.

Обязательная регрессия: существующие пересекающиеся уровни Keremet остаются читаемыми
и редактируемыми при сохранении прежних диапазонов (название/описание/процент), даже если
новые проверки запрещают новые пересечения. Не исправлять для этого реальные пороги,
не отключать всю валидацию, не ослаблять тесты и не делать конфликт молча «нормальным».
Если для совместимости требуется ещё незаданный продуктовый выбор — опиши точное препятствие.

## Проверки кандидата

- Проектные lint/typecheck, где настроены; адресные auth/admin/content/search проверки.
- Полный применимый backend-набор; отдельно объяснить известные baseline-падения, не скрывать
  их изменением ожиданий и не приписывать им новые регрессии без baseline-сравнения.
- SQLite и изолированный PostgreSQL: create/PATCH статуса без периода, новые независимые сессии,
  сохранение процента, прежние диапазоны Keremet, version/ETag, роли и tenant-isolation.
- Никаких тестов с угадываемыми общими БД, DROP FORCE чужих баз, production URL в pytest.
- Показать контракт, который примет локальный frontend, прежде чем его публиковать.

## После независимой приёмки: выкладка

Пройти свежий SSH/preflight, место, ревизию, защищённые копии, rollback image, сверку
snapshot, сборку и пересоздание только backend по исходному deploy-заданию.
Не менять env/compose/Caddy/Firebase, не ослаблять ACL и не запускать миграции в обход проверки.

Прежний `Permission denied` у Firebase не обходить sudo/другим пользователем/контейнером.
Сначала установи штатные возможности резервирования и сохранения нетронутого mount без чтения
секрета; изменение прежнего backup/preflight-порядка сначала опиши куратору как отдельное решение.
Если разрешённого способа нет — СТОП именно на выкладке, не бессмысленные повторные чтения.

После deploy проверить live-код/образ, health, сессии/контракт в доступной авторизованной
сессии, timezone, ошибки, права и отсутствие регрессии. 401 не доказывает поля ответа.
Не менять production-контент ради теста без согласованного тестового scope и восстановления.
Передать Gemini точную версию API и результат проверки, а не «вроде выложили».
