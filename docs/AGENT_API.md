# ONE Agent → Cloud Sync API Specification

Этот документ фиксирует контракт взаимодействия между локальным агентом торговой точки (ONE Agent) и облачным бэкендом (Cloud Backend).

---

## 1. Authentication

Каждый запрос агента обязан передавать персональный API-ключ в строго фиксированном HTTP-заголовке:

```http
X-Agent-Key: agk_<secret_token>
```

> **Примечание:** Заголовок `Authorization: Bearer` намеренно не поддерживается во избежание двусмысленности контракта. Используется исключительно `X-Agent-Key`.

### Безопасность и хранение ключа
* Ключ генерируется криптографически стойким генератором с префиксом `agk_`.
* В базе данных бэкенда хранится **исключительно SHA-256 хэш** ключа (`key_hash`). Открытый текст ключа в БД отсутствует.
* Открытый ключ выдается ровно один раз при создании или ротации агента.
* Ключ никогда не пишется в логи и не возвращается в ответах об ошибках.

### Tenant Isolation & Concurrency Safety
* Каждый агент намертво привязан к одному `business_id`.
* Тенант (`business_id`) для всех операций выгрузки карт и транзакций определяется **строго через API-ключ агента**.
* Запросы не содержат и не принимают `business_id` в теле (payload), что исключает возможность подмены или записи данных в чужой бизнес.
* **Атомарная блокировка на уровне тенанта:** При обработке пакетов карт и транзакций на уровне БД захватывается эксклюзивная блокировка строки бизнеса (`SELECT id FROM businesses WHERE id = :business_id FOR UPDATE`). Это гарантирует строгую сериализацию конкурентных запросов в рамках одного тенанта, защищает от race conditions и не создает блокировок между разными организациями.

## 2. Endpoints Contract

### 2.1. POST /agent/sync/cards

Прием пакета карт лояльности от ONE Agent.

* **Лимит пакета:** не более 500 карт за один запрос (`sync_max_cards_batch`).
* **Ключ карты:** цифровой штрихкод от 6 до 15 цифр (`^\d{6,15}$`), ведущие нули сохраняются.
* **Телефон:** нормализуется на стороне бэкенда к формату E.164 (`+77001234567`). Если телефон отсутствует — сохраняется `null`. Невалидный формат телефона вызывает ошибку `422 INVALID_PHONE_FORMAT`.
* **Баланс:** тип `Numeric(18, 4)` / `Decimal`. Бэкенд не рассчитывает баланс, а зеркалирует значение из 1С.

#### Stale Snapshot Protection (Защита от устаревших данных)
Если агент после сбоя сети присылает снимок карты со значением `updated_at`, которое меньше или равно уже сохраненному в облаке (`item.updated_at <= existing.updated_at`), этот снимок **не перезаписывает** более актуальные данные и учитывается в статистике ответа как `ignored_stale`.
Благодаря атомарной сериализации на уровне БД при одновременной отправке нескольких снимков разного возраста (например, 11:00 и 12:00) в базе данных **всегда** гарантированно сохраняется самое свежее состояние, вне зависимости от того, какой запрос первым получил CPU.

#### Пример запроса
```json
{
  "cards": [
    {
      "barcode": "0123456789012",
      "phone": "87001112233",
      "full_name": "Иванов Иван",
      "balance": "1500.5000",
      "is_blocked": false,
      "updated_at": "2026-09-29T10:00:00Z"
    }
  ]
}
```

#### Пример ответа (`200 OK`)
```json
{
  "received": 1,
  "created": 1,
  "updated": 0,
  "ignored_stale": 0
}
```

### 2.2. POST /agent/sync/transactions

Прием пакета бонусных операций (начисления, списания, корректировки).

* **Лимит пакета:** не более 1000 операций за один запрос (`sync_max_transactions_batch`).
* **Идемпотентность (включая concurrent replay):** композитный ключ `(card_id, external_id)` защищен на уровне базы данных. При параллельной отправке одинаковых транзакций оба запроса завершаются штатно (200 OK), ровно один создает запись, а второй фиксирует `duplicates`, без ошибок 500 и без `IntegrityError`.
* **Атомарность пакета (All-or-Nothing):** Обработка пакета выполняется в единой транзакции БД. Если в пакете обнаружен хотя бы один штрихкод карты, не существующей у данного бизнеса, запрос отклоняется с ошибкой `422 UNKNOWN_CARD_FOR_TRANSACTION`, и **ни одна транзакция из этого пакета не сохраняется в БД**. В сообщении об ошибке не раскрываются внутренние идентификаторы тенанта.


#### Пример запроса
```json
{
  "transactions": [
    {
      "external_id": "ONE-DOC-98765-LINE-1",
      "barcode": "0123456789012",
      "type": "accrual",
      "amount": "150.0000",
      "balance_after": "1500.5000",
      "occurred_at": "2026-09-29T09:55:00Z",
      "receipt_ref": "Чек №1234",
      "store": "Филиал Самал"
    }
  ]
}
```

#### Пример ответа (`200 OK`)
```json
{
  "received": 1,
  "created": 1,
  "duplicates": 0
}
```

### 2.3. POST /agent/heartbeat

Сигнал состояния агента (heartbeat каждые 60 секунд).

* Сервер фиксирует точное серверное время поступления сигнала в поле `last_seen_at`. Агент не может самостоятельно задавать это значение.
* Обновляются: версия агента (`version`), время последней успешной синхронизации по данным агента (`last_successful_sync_at`) и последняя зафиксированная ошибка (`error`).

#### Пример запроса
```json
{
  "version": "1.0.0",
  "last_successful_sync_at": "2026-09-29T09:55:00Z",
  "error": null
}
```

#### Пример ответа (`200 OK`)
```json
{
  "status": "ok"
}
```

### 2.4. Необязательное поле карты `spend_total`

`POST /agent/sync/cards` принимает `spend_total` (сумма покупок клиента в ONE, Decimal ≥ 0). По нему считается уровень лояльности. Если поле не передано, сохранённое значение не меняется.

### 2.5. POST /agent/qr/resolve (основной контракт для кассы)

`{"token": "C1..."}` → `{"card_id", "barcode"}`. Работает только для карт бизнеса этого агента. Просроченный или подделанный токен → `422 QR_TOKEN_INVALID`. Касса использует полученный `barcode` карты для дальнейшего начисления или списания стандартными кассовыми механизмами.

Для отдельного устройства Cash в LAN используйте [локальный POS-сервис агента](POS_QR_INTEGRATION.md): касса передаёт отдельный `X-Pos-Token`, агент обращается к этому облачному API со своим `X-Agent-Key` и возвращает только `barcode`. Ключ агента на кассу не передаётся; локальный сервис выключен по умолчанию.

### 2.6. Код подтверждения списания в WhatsApp (/agent/redemptions)

> **Не используется кассой (решение 2026-10-19):** списание выполняется кассой после сканирования QR/штрихкода, без подтверждения кодом. Эндпоинты сохранены в API как резервные.

1. `POST /agent/redemptions` `{"barcode" | "qr_token", "amount"}` → `201 {"redemption_id", "expires_at", "recipient"}`. Сервер отправляет 6-значный код владельцу карты в WhatsApp (номер привязанного клиента, иначе телефон карты). Лимит: 5 запросов на карту за 10 минут.
2. `POST /agent/redemptions/{id}/verify` `{"code"}` → `{"status": "confirmed", "barcode", "amount"}`. После этого касса проводит списание в ONE. Код живёт 5 минут, 5 попыток.

Ошибки: `REDEMPTION_PHONE_MISSING`, `CARD_BLOCKED`, `REDEMPTION_EXPIRED`, `REDEMPTION_MAX_ATTEMPTS_EXCEEDED`, `REDEMPTION_ALREADY_CONFIRMED`, `INVALID_CODE`, `WHATSAPP_NOT_CONFIGURED`.

## 3. Error Contract (Формат ошибок)

Все ошибки API возвращаются в едином структурированном виде:

```json
{
  "error": {
    "code": "STRING_ERROR_CODE",
    "message": "Human-readable explanation"
  }
}
```

### Коды ошибок
| HTTP Статус | Код ошибки | Причина |
|---|---|---|
| `401 Unauthorized` | `AGENT_KEY_MISSING` | Заголовок `X-Agent-Key` отсутствует или пуст |
| `401 Unauthorized` | `AGENT_KEY_INVALID` | API-ключ не найден в базе данных |
| `403 Forbidden` | `AGENT_REVOKED` | Агент отозван (`status != "active"`) |
| `422 Unprocessable` | `SYNC_BATCH_TOO_LARGE` | Размер пакета превышает допустимый лимит |
| `422 Unprocessable` | `UNKNOWN_CARD_FOR_TRANSACTION` | Штрихкод карты из транзакции не найден у тенанта |
| `422 Unprocessable` | `INVALID_PHONE_FORMAT` | Некорректный номер телефона у карты |
| `422 Unprocessable` | `VALIDATION_ERROR` | Ошибка схемы данных Pydantic (неверный regex штрихкода и т.д.) |
