# Gemini: упростить клиентский кабинет — первый этап, 2026-11-09

Ты исполнитель сайта и кабинета. Куратор независимо примет результат. Цель — сделать повседневную работу владельца магазина понятнее: найти клиента, изменить содержимое приложения, отправить рассылку, понять состояние связи. Меняем интерфейс роли `business_manager`; кабинет `superadmin` сохраняет существующие разделы и поведение.

**Упало или неожиданно — СТОП и сырой вывод; без самостоятельных исправлений и повторных мутаций; секреты и персональные данные скрыть.** Отчёт обязателен в файле. Никаких production-запросов с изменениями, настоящих рассылок, deploy, commit/push.

## Результат первого этапа

### Меню клиента

Четыре основных пункта: **Главная, Клиенты, Приложение, Рассылки**. Внизу отдельный второстепенный пункт **Настройки**.

- «Главная» использует текущий dashboard, «Клиенты» — текущие карты/клиенты, без изменения смысла данных.
- «Рассылки» — отдельный вход к уже существующим уведомлениям с таблицей и формой создания, включая отложенную отправку.
- «Приложение» — только баннеры/акции, магазины и тексты. Текущую вкладку рассылок клиенту убрать, поскольку она доступна отдельным пунктом.
- «Настройки» — небольшой экран со ссылками на существующие «Подключение» (агенты) и «Журнал событий». Не создавать новые формы настроек бизнеса и не добавлять полномочий.
- Существующие прямые адреса агента, журнала, карты и покупателя должны работать. Убираем технические пункты из основного меню, не меняем серверные разрешения. Выбранный раздел и подсветка меню должны корректно работать при перезагрузке и переходах назад/вперёд.
- `superadmin`: прежнее меню, вкладки, выбор бизнеса и действия сохраняются; новые клиентские маршруты не должны расширять доступ.

### Главная клиента

- Сохранить название магазина и три понятных показателя: «Карты», «Клиенты с картами», «Операции за период». Не называть `customers_with_business_cards` количеством установок приложения: API этого не доказывает.
- Показатель «Незаблокированные карты» убрать только с главной клиента. Остальные данные и страницы не удалять.
- Фильтр периода показывать компактно, сохранить текущую семантику и расчёт границ дат. Не вводить новые периоды, часовые пояса и метрики в рамках этой задачи.
- Блок «Состояние агентов» для клиента назвать «Связь с магазином», состояния перевести на простой язык. Не подменять актуальность балансов наличием heartbeat. Если dashboard возвращает только агрегаты, не выдумывать время связи и обновления: дать переход «Подробнее» к существующему подключению.
- У клиента убрать пояснения про `is_blocked`, read-only и Cloud Backend. Краткое полезное пояснение: «Баланс и операции обновляются после передачи данных из магазина». Не обещать мгновенное обновление или новый график синхронизации.
- Два прямых действия: «Найти клиента» и «Создать рассылку». Второе должно открывать настоящую существующую форму и корректно возвращаться к списку после закрытия.

### Приложение и рассылки

- Понятные подписи «Баннеры и акции», «Магазины», «Тексты приложения». Разделить выбор задачи так, чтобы владельцу не приходилось искать магазины под неопределённой вкладкой «Приложение» внутри «Приложения».
- Повторно использовать текущие редакторы и API, не переписывать бизнес-логику. Допустим небольшой рефакторинг компонентов для отдельных точек входа.
- Одно основное действие на выбранный раздел: добавить баннер/акцию, добавить магазин, сохранить тексты либо создать рассылку.
- Сохранить все поля, ограничения, RU/KK, загрузку изображений, сортировку, включение/отключение, подтверждение удаления. На этом этапе не делать обязательные поля необязательными и не придумывать автоматический перевод.
- В рассылках сохранить аудиторию своего магазина, переключение «Сейчас / В указанное время», валидацию, фиксированный UTC+5 и честный результат отправки. Не выдавать приём запроса провайдером за подтверждение прочтения или доставки на телефон.
- Предпросмотр приложения, новый поиск одновременно по телефону и карте, новые фильтры и новые функции — отдельные будущие задачи; сюда не добавлять.

## Оформление и границы

Сохранить Roboto, существующий бренд, стек и общую стилистику. Упрощаем навигацию и иерархию, не делаем полный визуальный редизайн. RU и KK равноценны. Десктоп и телефон: рабочие формы, меню, списки без горизонтального переполнения страницы, кнопки доступны, клавиатура и фокус работают. Не добавлять зависимости без необходимости.

Правки только `admin/`, этот промпт не переписывать; отчёт и снимки — в `reports/`. Не менять backend, миграции, агент, mobile, публичный лендинг, юридические страницы, ключи, конфиги, API-контракты, авторизацию и business scoping. Общие стили изменять так, чтобы не менять superadmin и лендинг. Использовать изолированные моки API для визуальной проверки; не входить в production и не отправлять реальные уведомления.

Для справки по библиотечным API использовать Context7: сначала resolve-library-id, затем query-docs по конкретному вопросу. При недоступности зафиксировать это; не считать локальное чтение исходников внешней документацией.

## Проверка и приёмка

После изменений: `npx vitest run --maxWorkers=1`, `npm run typecheck`, `npm run lint`, `npm run build`, `git diff --check`.

Содержательные проверки:

- `business_manager`: четыре основных пункта и второстепенные настройки; прямые адреса и детали карт/клиентов работают.
- `superadmin`: прежние разделы, выбор бизнеса и действия; чужие бизнесы клиенту не доступны, мутации не получают новый scope.
- Переходы в рассылки из меню и с главной, закрытие формы, обновление страницы, назад/вперёд; выделение текущего раздела.
- Сохранность существующих форм приложения и валидаторов отложенных уведомлений; сетевые ошибки не приводят к ложному успеху или потере ввода.
- Реальная страница кабинета с изолированными моками: RU и KK на 390 и 1366 px. Главная, клиенты, все подразделы приложения, рассылки (список и форма с датой), настройки, мобильное меню; отдельно контроль superadmin. Проверить пустые данные и ошибку API. Моки — не доказательство интеграции с настоящим backend.

Снимки до/после — `reports/client-cabinet-simplify-2026-11-09/`, не отдельный нарисованный HTML. Проверку делать в доступном браузере и указать инструмент. Если браузер недоступен — честно записать и не объявлять визуальную приёмку выполненной.
