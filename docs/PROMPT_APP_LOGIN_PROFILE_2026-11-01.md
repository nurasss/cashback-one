## 2. Код из 4 цифр

Установленные APK ≤ 1.0.8 принимают только 6 цифр (`^\d{6}$`, `maxLength={6}`). Если сервер начнёт слать всем 4 цифры, эти приложения не смогут войти. Поэтому длину выбирает клиент.

**Backend:**

- `SmsOtpRequest` и схема WhatsApp-запроса: необязательное поле `code_length: Literal[4, 6] = 6`. Проверь, что запрос без поля работает как раньше.
- `backend/app/core/security.py`: `generate_sms_otp(length: int = 6)`, с `secrets.randbelow` и ведущими нулями.
- `sms_auth_service.request_sms_otp` передаёт длину в генерацию.
- Проверка кода в `backend/app/schemas/auth.py`: `^\d{4}(\d{2})?$`. Обнови docstring и описания с «6-digit».
- **Лимит по IP на проверку кода, обязательно.** Сейчас у `/auth/whatsapp/verify` и `/auth/sms/verify` лимита по IP нет, есть только 5 попыток на код и 15 ошибок на номер за сутки. С 4 цифрами этого мало: с одного IP можно перебирать по разным номерам. Добавь через существующий `RateLimiter` лимит только на **неверные** попытки: `sms_otp_verify_ip_limit: int = 20` и `sms_otp_verify_ip_window_seconds: int = 600` в `config.py`. Посмотри, как получается IP в запросе кода, и повтори этот способ. Прежний лимит на номер и код ошибки не меняй. При превышении отдавай 429 тем же форматом ошибки, что у соседних лимитов.
- Выбери подходящий метод `RateLimiter`. Если счётчик в нём можно увеличить только вместе с проверкой, опиши это в отчёте и реализуй так, чтобы верный код не тратил лимит.

**Приложение:**

- `mobile/app/login.tsx`: запрос с `code_length: 4`, `maxLength={4}`, проверка `^\d{4}$`.
- `codeHint` в `ru.ts`/`kz.ts`: «Введите 4 цифры из сообщения», «Хабарламадағы 4 цифрды енгізіңіз».

Коды подтверждения кассы (`backend/app/schemas/pos.py`) и код входа по WhatsApp-challenge (`CHALLENGE_CODE_LENGTH`) не менять.

## 5. Автосохранение вместо кнопки

Поля из шторок уже сохраняются сами. Имя и фамилия сохранялись только по кнопке.

- Убери кнопку «Сохранить» и ключ `save`, если он больше нигде не нужен (проверь поиском).
- Имя и фамилия сохраняются сами: через 800 мс после последнего ввода, сразу по `onBlur`, сразу при уходе с экрана (`useFocusEffect` cleanup) и при размонтировании. На Android аппаратная кнопка «Назад» прячет клавиатуру без `onBlur`, поэтому одного `onBlur` недостаточно.
- Запросы идут по одному. Если во время PATCH текст изменился, после ответа уходит ещё один. Логику из комментариев в `save` сохрани: ответ применяется только к полям, где всё ещё тот же текст, а новый ввод не затирается.
- Ошибка: покажи `ErrorNotice`, текст в поле оставь, повтори при следующем изменении или уходе с экрана. Статус `saved` оставь, он показывается, только когда на сервере лежит то же, что на экране.
- Ожидающий таймер очищай при размонтировании, чтобы не было setState после ухода с экрана и лишних запросов в тестах.
