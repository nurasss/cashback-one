## 1. Доделать расстояния

Сейчас StatusStoresList умеет считать расстояние только из пропса userCoords, но оба вызова в status.tsx его не передают. expo-location не подключён, запроса разрешения и получения координат нет. Даже при координатах магазина с backend пользователь всегда увидит «Расстояние недоступно».

Подключить foreground expo-location для SDK55 (Context7 resolve/query). По явной кнопке «Показать расстояния» на списке магазинов запросить разрешение и получить текущую позицию с ограниченным ожиданием, передать в StatusStoresList. Если разрешение уже есть, допустимо обновлять по тому же действию; не запрашивать на холодном старте и не включать background. Никакой отправки координат пользователя backend/аналитике. Отказ, не спрашивать повторно, выключенный GPS, timeout, отсутствие координат у магазина — адреса и ссылки остаются, расстояние не выдумывать. Актуальные scopes/permissions/package-lock описать; новые foreground permissions явно ожидаемы по поручению владельца.

Контракт координат одобрен по форме: stores[].latitude/longitude — JSON number|null, парно, [-90;90]/[-180;180], из существующего GET /me/app-content. /app/content из черновика Gemini неверен, новый endpoint не придумывать. Отсутствие полей у старого backend допустимо. Прежде чем выполнять Haversine, проверить Number.isFinite и диапазоны, не выдавать NaN км; стабилизировать a в [0;1] для крайних координат. Реальные 0 м — допустимы, не превращать совпадение координат в 1 м. Не менять округление бонусов ради расстояний.

Ссылка «Где я могу потратить свои бонусы?» сейчас просто открывает начало /status. Она должна приводить к самому списку (route param + корректный scroll после layout либо отдельный раздел со списком в экране статуса), чтобы покупатель не искал адреса ниже длинного статуса. Без выдуманных фиксированных offsets, потерянного Back или автоскролла при обычном открытии статуса.

## 2. Ограничить весь запуск заставки

Сейчас AppSplash awaits mustWaitForConfig, resolveSplash дважды await readCache, затем await writeCache. CONFIG_TIMEOUT_MS ограничивает fetch, но не зависший AsyncStorage.getItem/setItem; в checking нет кнопки skip, поэтому приложение может остаться под overlay навсегда.

Ввести общий ограниченный бюджет проверочной фазы от монтирования (например 2 с), который завершает checking независимо от кеша/сети/записи, и защиту от поздних результатов. Чтение/запись кеша не должны блокировать показ или обычный запуск бесконечно; сохранение можно делать фоном с обработкой rejection. На checking также доступен выход/skip либо гарантированно срабатывает общий watchdog. Не отменять уже исправленный media timeout при ready. Последняя сохранённая заставка валидируется по тому же клиенту/формату; повреждённый кеш не передавать плееру как доверенный. Не вводить старую URL-зависимость.

Тесты управляемыми Promise: зависшие getItem, setItem, fetch; budget заканчивается и overlay снимается; поздний enabled/resolve не появляется поверх приложения и не повторяет запуск; размонтирование не создаёт обновлений; успешные image/video/skip и порядок UpdateDialog остаются.
