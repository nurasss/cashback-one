## 1. Посцентр: все шесть пунктов

### П1. Отступы всех применимых контролов

Инвентаризировать select, date/datetime-local, number, textarea, upload и их
встроенные кнопки в формах обеих ролей. Не считать собственный шеврон select
проверкой всех полей. Исправить реальные прилипания/наложения, сохранить нативную
доступность и клавиатурный ввод. Проверить Chrome и доступный альтернативный
движок, desktop/mobile; отсутствие движка указать, не устанавливать молча.

### П2–П3. Форма бизнеса: отображение и удобство

Не ограничиваться шириной 860 px. Сопоставить форму с обычными формами Keremet:
понятные подписи, связанные группы, адекватные поля, доступные действия, отсутствие
горизонтальной прокрутки, один понятный скролл и видимые ошибки у источника.
Технические поля цветов/префиксов/legacy-уровней не удалять и не терять данные.
Не заставлять пользователя править JSON в обычном сценарии: использовать
структурированные элементы для существующего допустимого контракта, сохраняя
неизвестные допустимые значения и семантику legacy-уровней. Если без изменения
backend-контракта это невозможно — описать конкретный блокер, не изобретать схему.
Не смешивать legacy loyalty_tiers бизнеса и BusinessLoyaltyTier каталога.
До финальной сборки показать целиком desktop/mobile форму со всеми группами,
ошибкой, длинными значениями и доступными Сохранить/Отмена, не один удачный фрагмент.

### П4–П5. Период, Назад и сообщение

Сохранить отсутствие ограничения длительности. Проверить malformed дату,
обратный диапазон и серверную ошибку отдельно. Назад возвращает рабочий Обзор,
сохраняет бизнес/роль/язык; повторное нажатие активной вкладки работает.
Проверить реальное поведение, не только наличие кнопки в DOM. Ошибка отделена
от полей на desktop/mobile. Многолетний допустимый диапазон отправляется в API.

### П6. Настоящая пагинация всех списков

Составить матрицу всех списков обеих ролей, включая бизнесы, агентов, карты,
клиентов, операции, акции, баннеры, магазины, статусы, рассылки и события.
Использовать существующую серверную пагинацию, а для уже полностью получаемых
небольших каталогов — клиентскую. Не создавать новый API ради локального списка.
Не выдавать раскрытие семи строк через Показать ещё за постраничную навигацию.
Для каждого списка проверить минимум две страницы, возврат, последнюю/пустую
страницу, фильтрацию со сбросом offset и обновление списка. Не терять записи
за пределом первой серверной страницы. Неприменимость пагинации обосновывать
для конкретного не-списка, а не исключать статусы/магазины молча.
Сохранить подпись Показать ещё там, где раскрытие остаётся, и раздельно показать
навигацию страниц. Не менять это требование обратно на Все (25).

## 2. Keremet: все пять пунктов

### К1. Редактирование шкалы и доставка

Посмотреть исходное видео, путь указан в reports/OWNER_ADMIN_ISSUES_TRIAGE_2026-11-16.md.
Понятная ошибка вместо общей не закрывает редактирование шкалы.
Claude готовит изолированный backend-кандидат и контракт целостного сохранения.
До получения и независимой приёмки его контракта не выдумывать endpoint/payload,
не добавлять запросы к несуществующему production API и не обходить пересечения.
Независимые П1–П6/К2–К5 выполнять сразу, не ждать Claude без работы.

границ с одним сохранением и явными ошибками, без ручной последовательности
нескольких PATCH и без автоматического переназначения соседних порогов.
Этот зависимый подэтап до получения контракта оставить открытым, а не PASS.

### К4. Сохранение новых баннеров/акций

Повторно посмотреть видео ошибки сохранения по исходному пути в triage.
Проверить полный сценарий обеих ролей: файл → создание → GET → reload/reopen →

Локальный InMemoryMediaStorage не доказывает production-загрузку.
Проверить клиентскую часть на изолированном принятом backend с реальными HTTP;
чётко оставить production-хранилище и физический Android открытыми до отдельного
согласованного доступа/тестовой области. Не публиковать проверочный контент Keremet.

### К5. Содержание событий

Проверить журнал обеих ролей на синтетических записях: создание/изменение/удаление
баннера, акции, статуса, магазина и доступных бизнес-настроек. Показать понятное
действие, объект и содержательное До/После для разрешённых пользователю полей,
а не только название или прочерк при фактическом изменении.
Сохранить tenant-изоляцию и серверную редакцию чувствительных полей. Не раскрывать
секреты, служебные ID/пакеты, лишние персональные данные или весь сырой JSON
менеджеру. Учесть null, неизвестный тип и историческую неполную запись:
честное Нет подробностей вместо выдуманного содержания. Если backend не отдаёт
безопасные необходимые данные — описать точный недостающий контракт для Claude.
