## 1. Лимит по IP ничего не блокирует (`backend/app/services/sms_auth_service.py`)

`is_rate_limited` вызывается только в ветке неверного кода. После превышения лимита неверный код даёт 429, а **верный код всё равно выдаёт токены**. Перебор продолжается: ответ 429 значит «не тот код», ответ 200 значит вход.

Исправление:

- В `RateLimiter` (Protocol), `InMemoryRateLimiter` и `RedisRateLimiter` добавь `is_blocked(key, limit, window_seconds) -> bool` **без увеличения счётчика**. Значение должно совпадать с `is_rate_limited`: заблокировано, когда следующий вызов `is_rate_limited` вернул бы `True`. In-memory учитывает скользящее окно. Redis читает `rate_limit:{key}` через GET, при ошибке Redis отдаёт тот же `AUTH_RATE_LIMIT_UNAVAILABLE`, 503.
- В `verify_sms_otp` проверяй `is_blocked` **в начале, до чтения записи OTP**. Заблокировано: 429 `RATE_LIMIT_EXCEEDED`. Попытка кода при этом не тратится.
- В ветке неверного кода только увеличивай счётчик и возвращай прежний `INVALID_CODE` или `OTP_MAX_ATTEMPTS_EXCEEDED`. 429 там больше не нужен.
- Верный код лимит не тратит.
- Найди поиском другие реализации `RateLimiter` в тестах и обнови их.

Тест: после исчерпания лимита **верный** код даёт 429, токены не выданы, запись OTP остаётся `pending`. После истечения окна тот же код проходит.

## 2. Лишняя цифра портит номер (`mobile/src/utils/format.ts`)

Воспроизведено куратором:

```text
phoneInputDigits('+7 701 123 45 678') → '0112345678'
phoneInputDigits('+ 701')             → '01'
```

Покупатель вводит 11-ю цифру в заполненное поле, и весь номер сдвигается. Сейчас после отбрасывания `+7` снова срабатывает правило 11 цифр.

Исправление: правило «отбросить первую из 11 цифр» применяется только если префикс ещё не отброшен. Префикс маски отбрасывается при `/^\+7/` или `/^7\s/` (стёрли плюс). При `+ 701` префикса нет: результат `701`.

Тесты: `+7 701 123 45 678` → `7011234567`, `+ 701` → `701`, `7 701` → `701`. Все четыре вида вставки из прошлого этапа остаются рабочими.

## 3. Устаревшее замыкание при очереди (`profile.tsx`)

`finally` вызывает `flushSave` из старого замыкания, где `profile.data` ещё до ответа. Сценарий: имя `A` → `AB` ушло на сервер, во время запроса покупатель вернул `A`. Повторный вызов сравнивает с устаревшим `A`, разницы не видит и показывает «Сохранено», а на сервере остаётся `AB`.

Исправление: в `flushSave` бери актуальный профиль из `query.getQueryData(keys.profile)`, а не из замыкания.

Тест: этот сценарий, последний PATCH содержит `A`.
