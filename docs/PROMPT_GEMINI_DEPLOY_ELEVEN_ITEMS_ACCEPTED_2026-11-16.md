## 5. Сначала backend

Проверить staging по всем 102 файлам. Выложить только принятый код, собрать
новый образ из staging, пересоздать только backend. Не запускать migration,
не перезапускать PostgreSQL/Redis/Caddy и не менять compose/.env.
Существующие задачи scheduler не должны дублироваться.

После переключения проверить:
- host/runtime-хеши принятого кода, фактический image digest и healthy;
- UID, неизменные read-only mount, Alembic по-прежнему 0019;
- health live/ready внутри и снаружи, отсутствие новых ошибок в безопасных логах;
- наличие зарегистрированных GET/PUT /admin/businesses/{id}/loyalty-tiers/scale
  в реально загруженном приложении и сохранение неограниченного периода статистики;
- без штатной сессии 401/403 не выдавать за успешную функциональную проверку API.

Если штатная сессия доступна — read-only GET шкалы своего разрешённого бизнеса,
аудита и /admin/me, без вывода чувствительных данных. Не выполнять PUT ради
проверки доступности, не использовать чужой реальный бизнес для негативного теста.
Если сессии нет — явно оставить HTTP-контракт под авторизацией открытым;
проверка runtime-маршрутов всё равно обязательна. Сессии не подделывать.

Только после успешных технических проверок backend продолжить frontend.
Не требуется отдельное промежуточное разрешение между этими двумя фазами.

## 7. Проверка работающего сайта

Чистый браузер, настоящий origin, без MOCK/route-перехватов API:
RU/KK × 1366×768 и 390×844, / и /admin/login.
Проверить загрузку ресурсов, отсутствие CONFIG_MISSING, видимую форму входа,
отсутствие переполнения, page errors и неожиданных сетевых/консольных ошибок.
Настоящий POST refresh обращается к https://api.cashback-qr.poscenter.kz;
401 без сессии ожидаем, но это не доказательство успешного входа.

При штатном доступе обеих ролей — read-only просмотр редактора бизнеса,
шкалы, пагинации/«Показать ещё», чекбоксов, журнала и ошибок дат/«Назад».
У manager не должно быть лишнего GET /admin/businesses с 403; у superadmin
выбор бизнеса остаётся. Проверить читаемость кнопки после перехода.

Это задание НЕ разрешает создавать/сохранять/удалять production-контент,
менять реальные пороги Keremet, статусы, магазины, карты и настройки,

## 8. Исключение для аварийного отката

До первого переключения подготовить точные команды и проверки отката.
При подтверждённой неисправности нового backend разрешён один code-only
откат на сохранённые код/образ/конфигурацию при отсутствии чужой выкладки,
без восстановления БД; проверить health и СТОП, frontend не начинать.

frontend на сохранённую базу, если HTML всё ещё принадлежит этой выкладке;
проверить HTTPS и вход, затем СТОП. Исправный новый совместимый backend
только из-за frontend-отката автоматически не откатывать; итог явно описать.
Чужое изменение или неудачный откат — СТОП без повторных мутаций.
