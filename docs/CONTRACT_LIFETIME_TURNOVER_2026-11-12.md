# Контракт: пожизненный оборот клиента (agent → backend) — 2026-11-12

**Статус: ПОДГОТОВЛЕН (готов к сверке). Не опубликован, не выкачен, на production не включён.**
Автор — Claude (backend). Потребители — Gemini (агент, admin). Основание — `docs/OWNER_LIFETIME_TURNOVER_UPDATE_2026-11-12.md`. Периоды, скользящее окно и понижение из-за неактивности **отменены**. Процент из ONE не передаётся: процент берётся из настроек статуса бизнеса.

Если реализация агента потребует чего-то, чего здесь нет, — СТОП и вопрос Claude, не придумывать несовместимый формат.

## 1. Принятое решение: накопительный snapshot, а не поток чеков

Агент передаёт **накопленный оборот по карте за всю историю** (подтверждённый snapshot) в уже существующем поле `spend_total` запроса `POST /agent/sync/cards`. Новых эндпоинтов, новой таблицы и **миграции нет**: используется существующий столбец `cards.spend_total NUMERIC(18,4) NULL`. Прежний довод против агрегатов (изменение окна) больше не действует.

Поток чеков/возвратов не вводится. Если ONE не даёт корректного агрегата — агент оборот **не передаёт** (см. §4).

## 2. Формат

`POST /agent/sync/cards`, элемент `cards[]` (остальные поля без изменений):

| Поле | Тип | Правило |
|---|---|---|
| `spend_total` | строка/число Decimal, до 4 знаков, ≤18 цифр, `>= 0`, либо поле **отсутствует** | Накопленная сумма покупок карты с начала истории, в валюте ONE (тенге). |

- Денежная точность: Decimal, не float. Агент сериализует строкой (`"1250000.5000"`), без округления до целых и без научной записи. Больше 4 знаков → 422 `VALIDATION_ERROR`, молча не округляется.
- Отрицательное значение → 422. Если ONE даёт отрицательную сумму, данные сомнительны: агент **не передаёт** поле (считать как неподтверждённое), а не обрезает до 0.
- Карта определяется `barcode` (4–13 цифр, ведущие нули сохраняются). Бизнес определяется **только** ключом агента; в теле запроса бизнес не передаётся и выбирать его нельзя.

## 3. Семантика значения

| В запросе | Смысл | Что делает backend |
|---|---|---|
| `"spend_total": "0.0000"` | **Подтверждённый полный ноль**: агент прочитал всю историю карты, покупок нет | Записывает 0 (если снимок свежий, §5) |
| `"spend_total": "<N>"` | Подтверждённый накопленный итог | Заменяет сохранённое значение на N (не прибавляет) |
| поле **отсутствует** | Агент не знает / не передаёт оборот (старый агент, источник недоступен, история неполная) | **Сохранённое значение не меняется**; у новой карты остаётся NULL = «неизвестно» |
| `"spend_total": null` | То же, что отсутствует (изменение относительно прежнего поведения, где `null` стирал значение) | **Сохранённое значение не меняется** |

Следствия:
- Ноль и «неизвестно» различаются: 0 = подтверждено, NULL = неизвестно. Агент **не имеет права** подставлять 0 вместо неизвестного: неполная история, недоступный регистр, ошибка чтения, карта без найденных строк в источнике, если полнота истории не подтверждена.
- «Подтверждение» — это сам факт отправки значения. Отдельного булевого признака в этой версии нет (нет места хранить без миграции). Агент включает отправку `spend_total` только когда источник и полнота подтверждены (см. §7).
- Сброс подтверждённого значения обратно в «неизвестно» через API **не предусмотрен**. Исправление оборота вниз/вверх — новым snapshot с меньшим/большим числом.
- Старый агент (без поля) не обнуляет и не меняет подтверждённый оборот — гарантируется и тестами.

## 4. Свежесть и защита от устаревшей доставки

Версия snapshot — существующее поле карты `updated_at` (aware datetime, UTC или с offset). Правило backend не меняется: если `updated_at` входящей карты **<=** сохранённого `updated_at` карты, **вся запись карты игнорируется** (`ignored_stale`), в том числе `spend_total`. Следствия:

1. **Повтор того же snapshot** (то же `updated_at`) ничего не меняет и не прибавляет оборот второй раз.
2. Устаревшая доставка (меньший `updated_at`) игнорируется целиком.
3. **Изменение только оборота** должно уйти с **более поздним `updated_at`**, иначе backend посчитает его устаревшим. Для карты с изменившимся оборотом агент должен отправлять `updated_at = max(время изменения карты в ONE, время чтения оборота агентом)`, монотонно не убывающее, aware, не из будущего.
4. Backfill оборота у уже отправленных карт — тоже с более поздним `updated_at`; состояние агента (SQLite/HMAC/курсоры) не сбрасывать; изменение оборота должно попадать в HMAC/обнаружение изменений карты.

### 4.1. РЕШЕНО И ПРОВЕРЕНО: гарантированная доставка после `ignored_stale` (совместное решение)

**Статус: РЕШЕНО И ПОДТВЕРЖДЕНО ТЕСТАМИ РАНТАЙМА (2026-11-12).**

Сетевой формат не меняется: backend по-прежнему возвращает агрегаты `{received, created, updated, ignored_stale}` без передачи списка штрихкодов.

Реализованный механизм агента (вариант «а» без изменения сетевого контракта и без миграций):
1. **Недопущение ложной фиксации и сохранение прежнего committed-состояния:** в `runtime._sync_cards_stream` при `ack.ignored_stale > 0` вызывается `source.discard_pending_batch(batch)` (метод `state_store.discard_pending_cards(session_id, page)`). Отвергнутый новый staged-хеш удаляется из `pending_cards` и **не фиксируется в `card_hashes`**. Если карта ранее уже была синхронизирована, её **предыдущий committed-хеш остаётся в `card_hashes`** (прежний хеш не удаляется искусственно). На следующем цикле 1С-воркер видит `content_hash != previous_committed_hash`, поэтому изменение оборота не теряется.
2. **Безопасность потока и курсоров:** курсор потока `commit_cursor("cards", batch.next_cursor)` штатно продвигается/фиксируется, предотвращая зависание потока (`SourceCursorStalledError`) и бесконечные немедленные повторы с тем же временем.
3. **Естественное продвижение времени и повторная доставка:** на следующем цикле синхронизации (когда время позволяет приём: `now_utc > dt_server`) источник 1С (данные которого не менялись) перечитывает карту. Поскольку карта либо отсутствует в `card_hashes`, либо её текущий хеш отличается от оставшегося старого committed-хеша, она распознаётся как изменённая и отправляется со свежей монотонной меткой наблюдения `updated_at = max(now_utc, dt_last + 1us)`.
4. **Смешанная пачка (mixed batch):** карты пачки, уже принятые сервером в первом цикле, во втором цикле безопасно и идемпотентно обновляются со свежим временем (`updated += 1`), а отклонённая ранее stale-карта успешно принимается сервером (`updated += 1, ignored_stale = 0`). После чистого приёма (`ignored_stale == 0`) пачка штатно переносится в `card_hashes`. На третьем цикле — 0 запросов.
5. **Состояние не сбрасывается:** SQLite (`agent_state.db`) и ключи HMAC не очищаются. Дата старого snapshot не фальсифицируется вслепую искусственными скачками в будущее — используется истинное монотонное время наблюдения агента.

**Подтверждено тестами на реальном runtime агента (`agent/tests/test_runtime_stale_retry.py`):**
- `test_mixed_batch_stale_retry_with_real_runtime_and_state_store`: смешанная пачка (Карта A stale, Карта B принята), SQLite на диске не сбрасывается, на цикле 2 Карта A успешно принята с оборотом `500000.0000`, на цикле 3 — 0 отправок.
- `test_existing_committed_hmac_stale_turnover_retry`: сценарий существующей карты с подтверждённым прежним оборотом; старый committed-хеш остаётся в SQLite; при изменении только оборота и stale на 1-м цикле карта на 2-м цикле успешно досылается и обновляет оборот в облаке.
- `test_single_card_stale_retry_with_real_runtime_and_state_store`: одиночная карта со stale-ответом и гарантированным повтором.
- `test_multi_page_batch_partial_stale_retry`: многостраничная пагинация (страница 1 со stale, страница 2 чистая) — страница 2 фиксируется, страница 1 безопасно досылается на следующем цикле.

*Граница доказательств:* тесты доказывают логику `AgentRuntime`, `OneComLoyaltySource` и дискового `StateStore`, но сетевой бэкенд Cloud и COM 1С в них являются программными имитациями (mock/simulated). Они не заменяют сквозную интеграцию с реальным production backend и пилотной базой 1С ONE (см. §7).

## 5. Ответ

Без изменений: `{received, created, updated, ignored_stale}`. Новых полей нет; агент не должен зависеть от дополнительных полей ответа.

## 6. Что backend делает с оборотом

**Уточнение UI владельцем 2026-11-13:** при наличии карты и отсутствии подтверждённого личного статуса приложение показывает минимальный уровень и его процент из применимого каталога бизнеса. Это отдельный запасной вариант отображения: ответы API `known=false` и неизвестный оборот не превращаются в подтверждённый статус или нулевой оборот. Серверные правила ниже не изменены. Решение и пределы: `docs/OWNER_LIFETIME_TURNOVER_UPDATE_2026-11-12.md`, дополнение от 2026-11-13; задача Claude: `docs/PROMPT_CLAUDE_MINIMUM_STATUS_FALLBACK_2026-11-13.md`.

- Хранит как есть (Numeric(18,4)). Не пересчитывает, не округляет, не вычитает возвраты сам.
- Статус карты определяется **отдельной** серверной функцией по накопленному обороту и активным уровням бизнеса (`business_loyalty_tiers`): выбирается активный уровень, диапазон которого `[min_turnover, max_turnover)` содержит оборот — нижняя граница **включительно**, верхняя **исключительно**, `max_turnover = null` — без верхней границы. Разрыв между диапазонами и значение выше последнего конечного `max` **не достраиваются соседним уровнем**: результат `known=false, reason="no_matching_tier"`. Непрерывность обеспечивается корректными соседними границами в настройках (например `[0; 350000)` и `[350000; …)`), а не расчётом. Для NULL — статус «неизвестен» (`known=false`, `reason="turnover_unknown"`), не первый уровень и не 0.
- Время и неактивность на статус не влияют: ничего не понижается из-за отсутствия покупок.
- Расчёт включается серверной настройкой `LIFETIME_TURNOVER_STATUS_ENABLED` (по умолчанию **выключена**); пока выключена, карта по-прежнему отдаёт `known=false, reason="unconfirmed"`.
- **Открытый вопрос владельца (не решён, не реализован):** снижает ли возврат/исправление, уменьшившее оборот, уже достигнутый статус, или достигнутый уровень сохраняется навсегда. Backend хранит текущий snapshot и считает по нему; политика «максимум навсегда» не реализована и не обещана. Агент оборот ради этой политики не искажает и не ограничивает.

## 7. Что в этом контракте НЕ подтверждено (ONE) и результаты исследования KONS2

Контракт определяет сетевой формат и семантику «значение/ноль/неизвестно». Он **не** утверждает, что ONE в текущем состоянии даёт полное и достоверное число по всем клиентам.

### 7.1. Результаты исследования тестовой ONE на KONS2
1. **Тип регистра:** регистр накопления `ПродажиПоБонуснымКартам` является **оборотным** (не остаточным). В нём присутствует реквизит `Активность`, но отсутствует `ВидДвижения`.
2. **Виртуальная таблица:** обращение к виртуальной таблице `РегистрНакопления.ПродажиПоБонуснымКартам.Обороты(, , , )` успешно выполняется платформой 1С. Ресурс виртуальной таблицы именуется `СуммаОборот`. Виртуальная таблица автоматически исключает неактивные записи (`Активность = Ложь`).
3. **Защита от дублей строк:** так как в регистре присутствуют дополнительные измерения, выборка из `.Обороты` без группировки может возвращать несколько строк на одну карту. В запросе агента реализована группировка:
   `СУММА(Об.СуммаОборот) КАК Оборот ... СГРУППИРОВАТЬ ПО Об.БонуснаяКарта`, исключающая размножение карт при `ЛЕВОЕ СОЕДИНЕНИЕ`.
4. **Неполнота тестовой базы:** на тестовой базе KONS2 обнаружено всего 8 записей по 3 картам из 1714. Причина отсутствия строк по остальным картам не установлена. Полнота боевой базы Keremet этим исследованием не проверялась.

### 7.2. Принципиальные ограничения доказательности
- **Отсутствие строк не доказывает пожизненный ноль:** если по карте нет записей в регистре оборотов, это означает лишь отсутствие движений в данной конкретной таблице, что может быть вызвано неполнотой выгрузки из касс Cash, отсутствием исторической миграции или разрывом в цепочке документов.
- **Положительный оборот тоже может быть неполным:** наличие ненулевой суммы (например, по 3 картам на KONS2 за ограниченный диапазон дат) не доказывает, что это весь пожизненный оборот клиента за все годы.
- **`ЕСТЬNULL(..., 0)` решает только техническую подстановку:** замена отсутствующего значения подзапроса на ноль предотвращает возврат `NULL` в строке выборки, но **не подтверждает полноту истории**.
- **Проблема неполноты истории НЕ решается заменой запроса:** переход на виртуальную таблицу `.Обороты` устраняет архитектурный дефект чтения физических строк, но не может восстановить отсутствующие в базе 1С первичные данные.

### 7.3. Порядок проверки полноты источника перед включением флага
Флаг `agent_lifetime_turnover_enabled` **строго остаётся `False`**. До его включения для любого бизнеса требуется выполнить регламент проверки:
1. **Технический срез базы бизнеса (read-only):** подсчёт доли карт со сформированным оборотом (`КартСОборотом / ВсегоКарт`), минимальной и максимальной даты движений в регистре по сравнению с датой старта программы лояльности.
2. **Сверка первичных документов и регистра:** для выборки контрольных карт сопоставить сумму чеков продажи/возвратов в кассовых сметах Cash с накопленным итогом в `ПродажиПоБонуснымКартам`.
3. **Анализ природы начальных остатков:** проверка наличия документов ввода начального оборота (например, `ДвижениеБонусныхКарт`) и их структуры.
4. **Решение о готовности источника:** флаг включается только при документальном подтверждении полноты данных в конкретной базе конкретного бизнеса уполномоченным куратором/разработчиком 1С. Включение вслепую запрещено.

## 8. Совместимость периода статуса (для admin)

Поле `turnover_period_months` в API статусов (`/admin/businesses/{id}/loyalty-tiers`):

- `POST` — поле **необязательно**. Админка создаёт статус без него и **не передаёт** скрытых фиктивных месяцев.
- `PATCH` — по-прежнему необязателен; если старый клиент пришлёт значение (1..36), оно сохранится как историческое (null по-прежнему отклоняется).
- Ответы (`GET`/`POST`/`PATCH`, `/me/app-content`) по-прежнему содержат `turnover_period_months` для совместимости со старыми потребителями. Это **историческое значение, в расчёте не участвует**; для статусов, созданных без поля, это служебный заполнитель столбца (столбец `NOT NULL`, миграция не делалась) со значением `1`, а не бизнес-правило. Админка поле игнорирует и не показывает.
- Проверка пересечения диапазонов оборота теперь выполняется **между всеми активными статусами бизнеса независимо от периода**: min включительно, max исключительно, `max > min`.
- Столбец БД не удаляется. Миграция «сделать столбец nullable / убрать заполнитель» — отдельное предложение, на согласование владельцем.

## 9. Проверки для Gemini

Admin: создание и редактирование статуса без периода; старое значение в ответе игнорируется.
