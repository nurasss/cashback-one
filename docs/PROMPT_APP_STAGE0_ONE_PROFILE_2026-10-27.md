Задача из двух частей. **Часть А** — на Mac: написать инструмент и тесты. **Часть Б** — на тестовом Windows: запустить инструмент на реальной ONE. ## Зачем это нужно

POSCENTER APP (`app.poscenter.kz`) — отдельный продукт, кабинет владельца магазина: продажи, остатки, взаиморасчёты. Сейчас данные из ONE попадают в него, когда обработку 1С запускают вручную. Хотим загружать их автоматически отдельным агентом, построенным на ядре агента лояльности Cashback One: Windows-служба, COM, только чтение, курсоры, очередь.

Перед разработкой нужен фактический ответ на вопросы:

1. В каких объектах ONE лежат продажи (чеки, строки, оплаты, возвраты), остатки и взаиморасчёты, и какие у них поля.
2. Какие объёмы данных и как быстро их читает COM.
3. Можно ли **без изменения конфигурации ONE** понять, что изменилось с прошлого цикла.

Этап 0 только собирает факты. Агент для APP на этом этапе не пишется.

### Что должен делать инструмент

Запуск: `python tools/app_stage0/app_stage0.py <команда> --output-dir <папка>`. Строка подключения берётся **только** из переменной окружения `ONE_CONNECTION_STRING`; её нет — понятная ошибка без подробностей. Флага `--connection-string` быть не должно.

Команды:

1. **`metadata`** — инвентаризация метаданных без чтения данных:
   - полный список имён и синонимов во всех категориях: `Документы`, `РегистрыНакопления`, `РегистрыСведений`, `Справочники`, `Перечисления`, `ПланыОбмена`, `Константы` (только имена и синонимы, без значений);
   - для объектов-кандидатов подробно: реквизиты с типами, табличные части с их реквизитами, для регистров — измерения, ресурсы, реквизиты, вид регистра (остатки/обороты), регистраторы; для документов — `Проведение`, движения по регистрам;
   - кандидатов находить эвристикой по именам и синонимам (продаж, чек, возврат, оплат, касс, смен, остат, товар, номенклатур, склад, взаиморасчет, контрагент, поставщик, покупател, долг, сотрудник, цен, себестоим, штрихкод), **плюс** уже известные `Документ.Чек`, `Документ.ОтчетКассовойСмены`, `Справочник.МестаХранения`, `Справочник.POS`. Эвристика — только подсказка, не доказательство: в отчёте пометить «кандидат, требует подтверждения».
   - отдельно: есть ли у документов и справочников-кандидатов поля, похожие на дату создания или изменения, и есть ли непустые планы обмена (только имена и состав, без регистрации изменений).

2. **`profile`** — агрегированный профиль данных по объектам из файла выбора `--targets <json>`. Файл формирует исполнитель в части Б по результату `metadata` (формат опиши в README). Для каждого объекта только агрегаты через `КОЛИЧЕСТВО`, `СУММА`, `МИНИМУМ`, `МАКСИМУМ`, `СГРУППИРОВАТЬ ПО`:
   - **документы:** количество по месяцам за последние 24 месяца и всего; доля проведённых, непроведённых, помеченных на удаление; дата первого и последнего документа (только дата); строк в табличных частях на документ (среднее, медиана, p95, максимум); число документов, где дата документа меньше даты последнего документа минус 7 дней, но которые есть среди 100 последних по `Ссылка`/номеру (признак ввода задним числом) — если так сравнить нельзя, написать почему;
   - **регистры накопления:** количество записей по месяцам за 24 месяца; для регистров остатков — число строк виртуальной таблицы `Остатки` на текущий момент, из них нулевых и отрицательных, число различных значений каждого измерения; для оборотных — количество строк `Обороты` за последний месяц;
   - **справочники:** количество элементов, групп, помеченных на удаление; для штрихкодов — только распределение длин и доля цифровых, без значений;
   - **оплаты:** различные значения вида оплаты (это значения перечисления или справочника, не персональные данные) и количество оплат по каждому за последние 3 месяца;
   - **`ВерсияДанных`:** читается ли в запросе для каждого ссылочного кандидата (да/нет и текст ошибки без данных).
   - **время**: для каждого запроса — длительность в мс и число строк результата. Отдельно «эталонная выборка»: прочитать (без вывода значений) строки чеков за **один** последний полный день и за **одну** последнюю полную неделю и посчитать строк в секунду через COM.

3. **`crosscheck`** — для владельца, только в локальную папку и **не** в репозиторий: сумма продаж и количество чеков за одну выбранную дату (`--date YYYY-MM-DD`), чтобы владелец сравнил с отчётом в самой ONE. В консоль и в отчёт — только «файл создан», без чисел.

Требования к коду:

- Перед выполнением каждый текст запроса проверяется: после удаления комментариев и пробелов начинается с `ВЫБРАТЬ` и не содержит `ПОМЕСТИТЬ`, `ДЛЯ ИЗМЕНЕНИЯ`, `УНИЧТОЖИТЬ`. Иначе исключение без выполнения.
- Каждый запрос в своём `try/except`: ошибка одного запроса записывается (тип и текст ошибки после `sanitize_text`) и не останавливает остальные.
- Ограничение длительности: если запрос шёл дольше `--slow-query-seconds` (по умолчанию 60), следующие тяжёлые запросы этого объекта пропускаются с пометкой «пропущено из-за медленного запроса». Тяжёлые эталонные выборки запускать последними.
- Выход: `metadata.json`, `profile.json`, `APP_STAGE0_SUMMARY.md` в `--output-dir`. Всё, что пишется в файлы и консоль, проходит `validate_safe_output`. Нарушение — исключение, файл не записывается.
- В JSON нет значений из данных: только имена метаданных, числа, даты без времени для границ периода и значения видов оплат.
- `--output-dir` обязателен; папка внутри репозитория запрещена (проверка в коде).

6. После работы: `Remove-Item Env:ONE_CONNECTION_STRING`. Снова `Get-Service POSCENTERLoyaltyAgent` и свежие строки `ONE read completed` (если читаются): служба работает, ошибок не прибавилось.
7. `git status --short` — в репозитории нет новых файлов, кроме отчёта.
