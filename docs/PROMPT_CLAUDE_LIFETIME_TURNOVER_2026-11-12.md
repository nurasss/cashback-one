# Claude: пожизненный оборот и персональный статус — локальный этап

## Цель и актуальные решения

Прочитай `AGENTS.md`, `CLAUDE.md`, `docs/OWNER_LIFETIME_TURNOVER_UPDATE_2026-11-12.md`, `reports/INNA_BACKEND_2026-11-12.md`, фактический diff backend/mobile и последние deploy-отчёты, если они появились. Более новый апдейт отменяет скользящие периоды и понижение из-за неактивности. Claude отвечает за backend и приложение; Gemini — за агент и admin. Старые промпты со скользящим окном не выполнять.

Агент должен дополнительно передавать накопленный оборот клиента из ONE, регистр `ПродажиПоБонуснымКартам`, ресурс `Сумма`, измерение `БонуснаяКарта`. Процент из ONE не импортируем. Backend определяет статус по пожизненному обороту и настройкам бизнеса. Пример 350/700 тыс. и 1/3/5% не зашивать в код и не применять автоматически к данным бизнеса. Балансы/карты/историю не обнулять. Применение процента на кассе — отдельный контракт, агент остаётся read-only.

## Что сделать сейчас

1. Прочитать текущую реализацию синхронизации (`backend/app/schemas/agent_sync.py`, `backend/app/api/agent_sync.py` и вызываемые сервисы), модели карт, `services/loyalty.py`, выдачу карточного статуса и `business_loyalty_tiers`. Проверь фактические пути. Зафиксируй baseline затронутых тестов абсолютным проектным Python, не системным. Сохрани текущие чужие правки, ничего не откатывай.
2. **Сначала подготовить для Gemini контракт** в `docs/CONTRACT_LIFETIME_TURNOVER_2026-11-12.md`. Рассмотри существующее необязательное `spend_total` вместо обязательного нового потока чеков: пожизненная схема допускает подтверждённый накопительный snapshot. Опиши денежную точность, карту, tenant из ключа агента, свежесть и защиту от устаревшей доставки, признак полноты/подтверждения, семантику отсутствующего поля и нуля. Старый агент без нового поля не должен обнулять подтверждённый оборот. Повтор того же snapshot не прибавляет оборот второй раз. Раздели контракт и неподтверждённую семантику ONE.
3. Убрать обязательность `turnover_period_months` для новых клиентов API создания/изменения статуса: админка должна создавать статус без этого поля. Не удалять столбец БД и не ломать старые запросы/ответы, пока есть потребители. Существующее историческое значение не использовать в расчёте. Зафиксировать выбранную обратную совместимость в контракте. Не подставлять скрыто выбранный период как новое бизнес-правило.
4. Локально реализовать принятые части контракта: приём достоверного накопительного значения с совместимостью старого агента и расчёт по активным уровням конкретного бизнеса. Использовать актуальные настройки уровней, не устаревший JSON-каталог как обход. Decimal; точные границы без дыр между 349999.99 и 350000.00; min включительно/max исключительно по действующему контракту. Для неполных/неподтверждённых данных — явно неизвестный статус, не ложный ноль/доказанный первый уровень. Неактивность/истечение месяцев само по себе ничего не уменьшает. Не включать расчёт на production.
5. **Открытый вопрос не додумывать:** владелец ещё не уточнил, снижает ли возврат/исправление достигнутый статус или сохраняется максимум навсегда. Подготовь обычный расчёт по заданному подтверждённому значению отдельной тестируемой функцией; политику изменения уже присвоенного уровня при уменьшении оборота не утверждай и не активируй. Не реализуй скрыто max-ever и не отбрасывай реальные исправления оборота. Если архитектура требует решения для интеграции — заверши подготовленные независимые части и назови точное место блокировки, не объявляй полный сценарий готовым.
6. В mobile только проверь совместимость существующего отображения статуса с контрактом и перечисли нужные изменения. Если потребуются изменения приложения, сначала представь отдельный небольшой план; не расширяй текущую работу и не собирай APK.

## Проверки и результат

Адресные тесты: без поля/ноль/неполная история, повтор snapshot, устаревшая доставка, изоляция бизнесов, сохранение баланса и bonus transactions, границы и дробные суммы, создание/редактирование уровня без периода, старый клиент с периодом, отсутствие понижения только от течения времени. Не маскируй неразрешённую политику возвратов фикстурами. Затем регрессия затронутых модулей; полные проверки при достаточном времени, без параллельных тяжёлых задач. PostgreSQL только отдельный тестовый кластер, не production. Известные Ruff/mypy проблемы отделять от новых.

Отчёт `reports/LIFETIME_TURNOVER_BACKEND_2026-11-12.md`: контракт, diff, реальные результаты проверок и логи, совместимость, готовое/непроверенное/заблокированное. Контракт для Gemini подготовь до остальных изменений и назови в финале. Сам исполнителя не запускай.

**Упало или неожиданно — СТОП и сырой вывод; без самостоятельных исправлений и повторных мутаций; секреты/ПДн скрыть.** Неверный путь чтения/пустой поиск разрешается уточнить и повторить чтение. Без deploy, ONE-запросов, изменений admin/agent, рабочих БД/состояния, новых миграций без согласования, APK/EXE, манифестов, commit/push. Предыдущая выкладка — отдельная задача: не подмешивать этот незавершённый функционал в её snapshot. После локального отчёта — СТОП для приёмки.
