## 1. Результаты аудита исходников

### Авторизация и зависимость от API

- Сейчас `main.tsx` монтирует `AdminProvider` над всем AppRouter. Provider создаёт QueryClient и AdminSession, подписывается на состояние и в effect вызывает `session.bootstrap()`. QueryClient создаётся без фонового запроса сам по себе; запрос запускается именно bootstrap.
- Bootstrap: `POST /admin/auth/refresh` с cookie, затем при успехе `GET /admin/me` с access token. До завершения view=`loading`. Refresh 401 переводит в `anonymous`; остальные ошибки, включая сеть, неверную конфигурацию URL и некорректный ответ, дают `error`. `RouterState` перехватывает loading/error/signing_out/logout_error до выбора маршрутов и заменяет ими любую страницу. Простое добавление LandingPage внутрь текущего RouterState проблему не решает.
- Login: `POST /admin/auth/login`, очистка приватного query-кэша, access token в памяти, затем `/admin/me`. При неуспехе access и кэш очищаются. 401 → anonymous, другие ошибки → error. Вход не должен быть условием доступа к публичной информации.
- Access token хранится в объекте AdminSession в памяти. Refresh-cookie передаётся с `credentials: include`; код учитывает HttpOnly и невозможность очистить её из JS. Не переносить access/refresh или пользовательские данные в localStorage, sessionStorage, URL или новый публичный контекст.
- `AdminApiClient` валидирует API URL при запросе, а не при импорте; конструктор и импорт transport/client сеть не вызывают. HTTPS обязателен, HTTP допускается только явно в dev. Каждый запрос имеет AbortController и таймаут 15 секунд, cache=`no-store`, заголовок `X-Admin-Request`. Неверная/отсутствующая настройка API превращается в ApiError, а не в обязательную ошибку загрузки публичного модуля.
- При 401 приватного запроса клиент делает совместно используемый refresh и одну повторную отправку; при отказе refresh с 401 очищает локальную сессию. 403 не вызывает refresh и сам по себе не делает сессию anonymous. Глобального `window.location`-редиректа в transport/client нет: переход на вход выполняет RequireAdmin по состоянию сессии.
- Query hooks обращаются к API при монтировании соответствующих административных компонентов. При импорте `queries.ts` запросов нет. На лендинге не нужны ни эти hooks, ни SessionContext, ни QueryClientProvider, ни Content API.
- Logout сначала переводит view в signing_out, увеличивает epoch, очищает access и приватный кэш, затем отправляет `POST /admin/auth/logout` без bearer. Успех → anonymous; ошибка → logout_error. Ошибка поглощается внутри logout, поэтому `AdminLayout.signOut()` после await всё равно вызывает navigate('/login'), но RouterState продолжает показывать экран неподтверждённого выхода. Это поведение блокировки нужно сохранить; смена адреса сама по себе не доказывает отзыв cookie.
- Проверка поколения защищает часть поздних ответов сессии; отмены bootstrap при размонтировании provider сейчас нет. В первом пакете переходы между публичной и административной поверхностями предлагаются обычными ссылками с полной навигацией документа. Это не вводит новые гонки SPA-размонтирования provider во время login/logout. Внутри кабинета остаётся клиентская навигация.

В исходниках нет сохранения исходного пути перед входом и нет returnTo. Текущий вход всегда ведёт в Dashboard. Поэтому безопасный возврат к исходной странице **не является обязательной частью первого пакета**: это дополнительная функция, а не восстановление существующей. Никаких returnTo из query без отдельного проектирования.

Backend в трёх местах `services/admin_mutations.py` выдаёт `settings.admin_public_url` без добавления `/admin/login`. В `core/config.py` значение по умолчанию пустое; после нормализации fallback — первый admin_allowed_origin либо корень `https://cashback-qr.poscenter.kz`. Фактическое production-значение неизвестно, env не читался. Старые уже выданные ссылки на корень неизбежно станут вести на лендинг: на нём сразу виден вход для бизнеса. Фронтенд кабинета обслуживается на том же origin; поэтому каноническая same-origin ссылка в ManagerAccessDialog решает выдачу новых ссылок из этого интерфейса без изменения backend. Внешние потребители API по-прежнему получат configured login_url; изменение backend настройки/контракта — отдельная задача, не скрытая часть frontend-пакета.

### Хостинг и rewrite

- `docs/DEPLOY_VPS.md` описывает отдельный статический Plesk-хостинг для корня, сборку `admin/dist`, FTPS и соседние `app/`, `demo/`. API размещён на другом origin/VPS. Vite config не содержит пользовательских rewrite или отдельного production-сервера; dev fallback не доказывает поведение хостинга.
- Локальная копия действующего `.htaccess` в проверенном репозитории не найдена. `docs/HANDOFF_2026-10-19.md` прямо отмечает отсутствие копии; последующие отчёты фиксируют сохранение remote `.htaccess`. Нельзя воспроизвести реальные RewriteRule/RewriteCond, исключения файлов/каталогов, HTTPS, CSP и Cache-Control по этим упоминаниям.
- `upload_admin.py` перечисляет **все** файлы из `admin/dist`, сортирует index последним, загружает их относительно site_dir. Удаления удалённых файлов нет; `.htaccess` только проверяется и сохраняется. Аргумент `--with-htaccess` объявлен, но не используется для генерации правил. Это не средство настройки SPA rewrite.
- Одинаковый размер hashed asset считается достаточным для SKIP; контроль содержимого этим не доказан. Загрузка идёт прямым STOR; для index в текущем скрипте нет временного имени и atomic rename. Отчёт TASK_040 описывает отдельную публикацию через временное имя — не переносить этот факт на общий uploader.
- Даже `--dry-run` читает секретный env, подключается к FTPS и **до выхода dry-run сохраняет копию удалённого index в локальный `C:/cashback-stage0/...`**. Поэтому его нельзя запускать в этом read-only аудите. Этот факт установлен чтением, запусков не было; содержимое существующего `C:/` не исследовалось, происхождение не утверждается.
- Скрипт не имеет защитного allowlist от `dist/app`, `dist/demo`, `.htaccess` и иных случайных файлов. Отсутствие delete не защищает от перезаписи одноимённых файлов. Нужен контроль состава артефакта перед отдельным деплоем; в первом пакете uploader не менять и не запускать.
- Старый документ утверждает кэш assets на 10 лет. Это историческая инструкция, а не измеренные актуальные заголовки. Политика HTML и наличие server-side исключений остаются неизвестными.

Вывод: frontend-разделение можно спроектировать и реализовать локально без смены сервера. **Готовность к публикации нельзя подтвердить**, пока действующие правила раздачи `/admin/*`, `/app/*`, `/demo/*` и кэш не будут проверены в отдельно разрешённом этапе. Недоступность конфигурации — ограничение доказательств, а не повод придумывать или заменять `.htaccess`.

## 3. Визуальное направление

Предложение: светлая продуктовая страница с акцентом на карте покупателя. Один крупный реальный экран приложения, ясная типографика и небольшое количество акцентных элементов. Первый экран одновременно объясняет назначение и даёт скачать APK; вход для бизнеса визуально вторичен, но доступен сразу.

В исходниках есть знак POSCENTER, логотипы и красный `theme-color: #ff3a4d`. Это основание для предварительного направления, но не доказательство актуальной палитры мобильного приложения. Перед реализацией сверить действующие mobile-токены и брендовые изображения. Базово: белый/светлый фон, тёмный текст, подтверждённый красный для основного действия. Использовать существующий шрифт либо системный стек с хорошей кириллицей, без внешнего сервиса шрифтов.

Композиция: просторный первый экран с телефоном; затем текстовая последовательность действий; отдельный заметный блок о задержке баланса; широкая секция для бизнеса; спокойный список FAQ. Избегать ряда одинаковых карточек с иконками, декоративных графиков, градиентных пятен, стеклянных панелей, выдуманных логотипов и карусели отзывов.

Изображения брать из текущего приложения после проверки и обезличивания. Не публиковать реальные имена, телефоны, номера карт, рабочие QR/штрихкоды и балансы клиентов. Макеты с условными значениями явно подписывать «Пример интерфейса». Пока согласованных изображений нет, не придумывать экраны и функции.

На телефоне — текст и CTA перед изображением, без горизонтального скролла; удобные зоны нажатия, видимый фокус, читаемый основной текст. FAQ возможен на нативном details/summary. Для этого этапа макеты, изображения и новые файлы не создаются. Визуальные рекомендации предварительные: браузерный снимок не получен; автоматический дизайн-инспектор не запускался из-за ограничения на изменения и последующего STOP.

## 4. Рекомендуемая архитектура и точный первый пакет

### Архитектурное решение

Оставить существующую сборку `admin/` и существующие зависимости. Один BrowserRouter выбирает маршрут **до монтирования AdminProvider**:

- `/` → LandingPage, локальный контент и прямой APK href;
- явные старые административные адреса → replace-переход на канонический адрес без провайдера;
- `/admin/*` → отдельно загружаемый AdminRoutes, внутри AdminProvider, обработка session view, LoginPage, RequireAdmin и страницы кабинета;
- остальные URL → публичный 404 без авторизации.

Перенести административные импорты и обработку RouterState из общего AppRouter в `layout/AdminRoutes.tsx`. Общий AppRouter не импортирует сессию, API, Query и приватные страницы напрямую. Лендинг открывается независимо от cookie, API URL, refresh, /me, отказа сети и существующей авторизации. Не перенаправлять авторизованного посетителя с `/` в кабинет автоматически. Граница загрузки административного модуля имеет собственный fallback ошибки; ошибка кабинета не должна лишать доступа к публичной странице.

Шапка/CTA лендинга открывают `/admin/login` обычным `<a>`. Если потребуется отдельная ссылка из кабинета на публичную страницу — тоже обычный `<a href="/">`, а не SPA-переход. Внутренний логотип кабинета ведёт в `/admin`. Это намеренная граница документов в первом пакете: не переиспользовать auth-state и query-кэш между поверхностями, не добавлять dispose/cancellation в модель сессии ради лендинга. На экране logout_error не показывать успешный выход; повторный logout остаётся доступен, доступ к приватным страницам закрыт. Открытие публичного сайта не является отзывом HttpOnly-cookie и не должно называться выходом.

CSS кабинета сейчас задаёт `:root`, body, ссылки, кнопки и поля глобально; отложенная загрузка CSS сама по себе не изолирует селекторы. В первом пакете перенести административные токены и общие правила под внешний `.admin-surface`, охватывающий login, ошибки и кабинет; оставить общему документу минимальные нейтральные reset-правила. Стили лендинга ограничить `.landing-page`. Убедиться, что портал диалогов получает административный контекст CSS; фактическую точку портала проверить перед этим изменением. Не менять визуальный дизайн кабинета. Проверка CSS-теста должна следовать новому корректному scope, сохраняя проверку целостности файла.

Публичное содержимое в первом пакете — клиентский LandingPage плюс короткий `<noscript>` в общем index: назначение, задержка обновления баланса, прямая APK-ссылка и пояснение, что для кабинета нужен JavaScript. Полная статическая генерация страницы, SSR, новые build-плагины и второй HTML entry **не входят** в первый пакет. Это уточняет прежнее предложение о полном статическом HTML: независимость от API обязательна сейчас, полноценное SEO/prerender — отдельное улучшение. Не заявлять доступность при отказе самого хостинга или загрузки общего JS.

### Схема URL

| Адрес | Поведение |
| --- | --- |
| `/`, `/#how-it-works`, `/#business`, `/#faq` | Лендинг и его секции, без AdminProvider и auth-запросов |
| `/admin`, `/admin/` | Dashboard; при anonymous → `/admin/login` |
| `/admin/login` | Вход; authenticated/успешный login → `/admin` |
| `/admin/businesses`, `/admin/businesses/:businessId` | Страницы бизнеса с RequireSuperadmin |
| `/admin/agents`, `/admin/agents/:agentId` | Существующие страницы агентов |
| `/admin/operations`, `/admin/cards/:cardId`, `/admin/users/:userId` | Список, карта и профиль |
| `/admin/audit`, `/admin/content` | Существующие страницы журнала и контента |
| `/login` | Replace → `/admin/login` |
| `/businesses`, `/businesses/:businessId`, `/agents`, `/agents/:agentId`, `/operations`, `/cards/:cardId`, `/users/:userId`, `/audit`, `/content` | Явное соответствие под `/admin`, без промежуточного bootstrap |
| Неизвестный `/admin/*` | 404 внутри административной ветки, без отправки на лендинг |
| Прочие неизвестные адреса | Публичный 404 без bootstrap |
| `/app/*`, `/demo/*` | Зарезервированные пространства существующей раздачи хостинга, без новых клиентских страниц и redirect-правил |

Legacy-переходы сохраняют query и hash, включая старый `/login`; ID не теряются и не кодируются повторно. Варианты с завершающим `/` включить в тестовую матрицу. Сессия и права проверяются уже на каноническом адресе. После входа по старой глубокой ссылке пользователь получает `/admin`, как и при прежней логике входа в Dashboard; автоматический возврат к деталям не обещается.

Корень не может одновременно быть лендингом и прежним Dashboard. Старые закладки и приглашения на `/` сохраняют возможность входа через заметную кнопку. Это единственное намеренное изменение назначения существующего URL. Клиентская маршрутизация не гарантирует сохранность реальной раздачи `/app/` и `/demo/`: гарантия до публикации требует проверки server rewrite и состава загрузки.

### Состав первого пакета после отдельного поручения на реализацию

Обязательный результат: одна полноценная публичная страница по разделам 2–3, независимая от API; канонический кабинет; совместимость старых URL; регрессионные проверки. Пакет локальный и без деплоя.

| Файлы | Точный характер изменений |

| **Новый** `admin/src/pages/LandingPage.tsx` | Все утверждённые тексты, FAQ, навигация, повторные CTA; без загрузки контента с API |
| **Новый** `admin/src/styles/landing.css` | Адаптивные публичные стили, минимальный общий reset; не использовать классы кабинета |

| `admin/src/features/AdminMutations.tsx` | В ManagerAccessDialog показывать и копировать один канонический same-origin URL `/admin/login`; пароль и одноразовый режим не менять |

Новых изображений в обязательном первом пакете нет: использовать уже имеющиеся безопасные брендовые материалы и текстовую композицию. Если подтверждённый обезличенный экран приложения ещё не передан, не генерировать фиктивный интерфейс ради hero. Отдельное добавление скриншота может быть согласовано позже, без изменения продуктовых обещаний.

Изменения **не требуются** в `auth/provider.tsx`, `auth/session.ts`, `api/transport.ts`, `api/client.ts`, `api/queries.ts`, backend, mobile, agent, package.json/lockfile, vite.config.ts, uploader, `.htaccess`, содержимом `/app/` и `/demo/`. Их чтение не является разрешением на правки. Component-тесты content/cards/mutations, использующие локальные MemoryRouter и AdminProvider напрямую, не надо массово переписывать под публичный root: они не тестируют production-маршрут. `session.test.ts` остаётся регрессией без смены auth-контракта.

## 5. Критерии приёмки первого пакета

Это план будущей проверки, а не результаты уже выполненных тестов.

1. **Публичная доступность.** На холодном `/` нет вызовов API, refresh, /me, session hooks и QueryProvider. Проверить без API env, с неверным URL, при offline/timeout/500 API и с существующей cookie. В каждом случае доступны тексты, FAQ и `/app/cashback-one-1.0.2.apk`; URL не меняется на login. Не выполнять реальный refresh ради этого теста.
2. **Изоляция загрузки.** Приватные страницы/данные не загружаются на `/`. Искусственный отказ загрузки административного модуля локально не препятствует открытию лендинга. Переходы между поверхностями — полная навигация документа; внутренние переходы кабинета работают без лишнего пересоздания provider. В публичном тексте нет реальных данных сессии.
3. **Вход.** `/admin/login` сохраняет bootstrap до показа формы. Refresh 401 → форма, успех → `/admin`; после login — `/admin`. Сеть/конфигурация/500 → безопасный экран с повтором и существующим continueToLogin. 403 не превращать в разрешение доступа. На публичный `/` эти состояния не распространяются.
4. **Выход и отказ.** Сразу очищаются локальные credentials/cache; до подтверждения сервером private UI закрыт. Неудачный logout остаётся logout_error с повтором и не называется успешным выходом. Повтор успешен → `/admin/login`. Проверить поздние ответы запросов; не ослаблять epoch/single-flight и текущие проверки privacy.
5. **Маршруты и роли.** Прямые входы, reload, back/forward, все legacy aliases и trailing slash; query/hash и ID сохраняются, циклов нет. Меню, логотип, Dashboard, AccessDenied, детали и возвраты не ведут на публичный `/`. Superadmin и business_manager сохраняют свои права. Неизвестные адреса дают соответствующий клиентский 404 (это не обещание HTTP 404 на статическом fallback).
6. **Ссылки менеджера.** Показ и буфер обмена в ManagerAccessDialog содержат одинаковый текущий origin + `/admin/login`; одноразовые данные не попадают в хранилища и публичный контент. Старое приглашение на `/` открывает лендинг с видимым входом. Уточнение для внешних потребителей backend login_url отражено как ограничение, без скрытой смены server config.
7. **Содержание и доступность.** Объяснение продукта, кнопка Android, вход, порядок работы и FAQ присутствуют; задержка баланса заметна вне FAQ. Нет тарифов, отзывов, чисел тестовой базы, мнимой регистрации, ссылок Wallet/магазинов приложений и обещания работы любой кассы. На 320/390 px, планшете и ноутбуке нет горизонтального скролла; клавиатура, focus, заголовки, контраст, zoom 200%, reduced motion. При выключенном JS видны краткое объяснение и прямая APK-ссылка из noscript. Полный лендинг без JS не является критерием первого пакета.
8. **Регрессия и сборка.** Перед кодом baseline в `admin/`: `npm test`, `npm run typecheck`, `npm run build`; после — те же проверки. Сбой baseline или новая неожиданность → STOP, безопасный сырой вывод, без изменения фикстур для сокрытия. Существующие session/transport/privacy-тесты сохраняются. Никаких установок зависимостей без отдельного поручения. Для аудита эти команды не выполнялись.
9. **Проверка границ артефакта.** В будущем dist нет новых `app/`, `demo/`, `.htaccess`, секретных env, backup и рабочих данных. Ссылки на зарезервированные пути — обычные href, не React-страницы. Отчёт реализации явно перечисляет изменённые файлы и ограничения. Изменение backend/модели сессии/пакетов означает выход из объёма первого пакета.

### Отдельные условия перед будущей публикацией

Нужны отдельное поручение и проверка реальных server rewrite/headers без чтения секретов в чат. Существующие `/admin` и глубокие ссылки должны отдавать SPA shell, существующие `/app/*` и `/demo/*` — свои файлы/приложение, а не лендинг. Зафиксировать HTTP-статус, Content-Type и отсутствие перенаправления APK в HTML; проверить сами старые ссылки и demo. Не полагаться на Vite dev server как доказательство.

Перед публикацией — копии изменяемых файлов, allowlist по фактическому dist и неизменяемый список исключений `/app/`, `/demo/`, APK, `.htaccess`. Assets сначала, index последним через отдельно подготовленный безопасный способ; существующие chunks не удалять, не менять hashed-файлы под прежним именем. Проверить содержимое/хеши, а не только совпадение размера. Сейчас это требования к следующему этапу, не разрешение запускать uploader или дорабатывать его.

| Актуальные Cache-Control/CSP и HTTP fallback | Не измерены. Отдельно проверить перед публикацией, особенно index/chunks и прямые `/admin/*` |

Открытые эксплуатационные и визуальные вопросы перечислены явно. Реализация, деплой, commit/push и изменения production этим отчётом не выполнялись и не разрешаются.
